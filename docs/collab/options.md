# Options: протокол совместного редактирования для CADCraft

> Артефакт Phase 0 к `study.md`. Три варианта, различающиеся **механизмом**
> (кто и что применяет, что летит по сети), а не настройками. Рекомендация — в §4.

- Проект: `cadcraft`
- Upstream-коммит: `a655cee0` (см. `study.md`)
- Дата: 2026-11-06
- Автор: `cadcraft/envoy`

## 1. Что задаёт ограничения (факты из `study.md`)

1. Правка — произвольная Rust-функция `run(&mut Session, &Value)`
   (`crates/engine/src/cmd.rs:69`), а не данные. Параметры JSON, но эффект
   зависит от состояния сессии.
2. После каждой undoable-команды движок делает глобальные пост-проходы:
   группы, **параметрический решатель** (`cmd/constraints.rs:1136`) и
   ассоциативные размеры (`assoc.rs:402`). Одна команда может изменить
   неограниченное множество сущностей, и результат порядко-зависим.
3. Модель уже COW: `EntityStore` — чанки по ≤1024 сущности, клон O(1), правка
   копирует один чанк (`doc/src/store.rs:22`); `same_as`/`chunk_slices` дают
   дифф «только изменённые чанки» (`store.rs:271`).
4. У сущностей есть стабильный ID — `Handle(u64)`, выдаётся сервером из
   `handseed` и переживает save/load (`doc/src/lib.rs:213`). У слоёв/блоков/
   стилей/layout — только имя, переименование каскадно по всему чертежу
   (`cmd/props/rename.rs:21`).
5. Undo — снапшот всего `Arc<Drawing>` на документ (`doc_state.rs:5`), не на
   пользователя и не сериализуется.
6. Геометрия — f64 без допусков; `LUNITS/LUPREC` только отображение. По сети
   надо возить точные f64 (`serde_json` с `float_roundtrip`).
7. Derived-данные: блоки `*D`/`*T` генерируются при записи
   (`io/src/dxf_write/blocks.rs:19`), ассоциативные размеры и ограничения
   пересчитываются пост-проходами. В дельте их везти не нужно — но и
   «пересчитать у себя» нельзя без гарантии одинакового входа.
8. Запись: DXF 2000–2018 своим писателем, DWG — мостом `acadrust` **в дочернем
   процессе** (`io/src/lib.rs:65`). Потери на записи уже считаются
   (`loss_on_save`, `cmd/file.rs:835`). WASM: без DWG, без потоков.
9. Прямых сетевых зависимостей нет (`tokio` есть в `Cargo.lock` только
   транзитивно через `wasm-bindgen-futures`, не используется). Есть общий
   web-мост `craft-web-host` (`apps/cadcraft-web/src/host.rs`).

## 2. Три варианта

### Вариант A — реплей команд (client-side replay)

Клиент выполнил действие → отправляет `{command, params}` → **каждый** клиент
вызывает `Session::execute(id, params)` у себя; сервер — арбитр порядка и
раздатчик `version`.

- Плюсы: переиспользует зарегистрированные команды (422 конструктора `CommandSpec`); клиент видит свой результат мгновенно
  (0 RTT); просто писать.
- Минусы: пост-проходы (решатель, ассоциативность, группы) зависят от полного
  состояния чертежа → при малейшем расхождении состояния (undo, presence-правка,
  пропущенная операция) чертежи расходятся **без ошибки**; команды читают
  сессионные поля (`space`, `CLAYSPACE`, `last_used`, выбор) — их пришлось бы
  синхронизировать целиком; undo остаётся глобальным; viewer может исполнить
  команду локально; откат невозможен (инверсий нет).
- Когда годится: только детерминированные команды без пост-проходов и при
  жёсткой гарантии одинакового состояния (по сути — CRDT-подобная база).

### Вариант B — серверный op-лог: интент на вход, дельта модели на выход

Клиент присылает **намерение** (`command` + params + контекст пространства либо
нормализованный op), исполняет его **только сервер** (headless `Session` на
чертёж). Сервер снимает до/после, диффит по чанкам и рассылает **дельту
модели**: `create/replace/delete` сущностей, табличные операции, порядок
отрисовки, — с номером версии.

- Плюсы: вся семантика CADCraft (пост-проходы, derived-блоки, `loss_on_save`)
  остаётся в одном месте; сходимость тривиальна — у сервера единственная
  копия; дельта не содержит производных данных; `handle` выдаёт сервер → нет
  коллизий; per-user undo = инверсии дельт; роли и лимиты проверяются на
  сервере; дифф ограничен изменёнными чанками.
- Минусы: своя латентность на правку (показ оптимистично + откат, либо
  «карандаш» поверх, как в CAD); нужен словарь дельт и диффер; интент-команда
  должна быть разрешена явно (не все команды безопасны в общем чертеже:
  `open`, `saveas`, `quit`, `new`, `recover`, LISP — запрещены).
- Цена: средняя. Основная работа — не транспорт, а (а) список разрешённых
  интентов, (б) дифф по чанкам, (в) инверсии для undo.

### Вариант C — CRDT по полям сущностей

Свойства сущностей — LWW-регистры, коллекции (слои, блоки, порядок) — OR-set
с идентификаторами записей; слияние на клиентах, сервер хранит лог для
истории/commit.

- Плюсы: оффлайн и P2P; нет RTT на правку; сходимость при любом порядке.
- Минусы: модель CADCraft сопротивляется CRDT: (1) геометрия сущности —
  атомарный `EntityKind`, поля связаны (радиус/центр дуги, вершины/bulge),
  LWW по полям даст геометрически невозможные состояния; (2) имена слоёв/
  блоков — идентификаторы ссылок, OR-set имён не решает «удалили слой —
  переехали сущности»; (3) derived-блоки, ассоциативные размеры и глобальный
  решатель ограничений в CRDT не выражаются без полного пересчёта на каждой
  реплике — то есть нужен тот же авторитетный пересчёт; (4) персистентность
  всё равно серверная (файл, версии, `notSaved`); (5) объём: своя CRDT-библиотека
  под house rules (без `unsafe`, без паник) — недели, либо тяжёлая чужая
  зависимость и несовместимый с WASM-бюджетом размер.
- Когда годится: если бы правки были независимыми по полям и не было
  глобальных пересчётов.

## 3. Сравнение

| Критерий (AGENDA) | A: реплей | B: серверный op-лог | C: CRDT |
|---|---|---|---|
| 1. Round-trip формата не ломается | Пишет тот же движок, но при расхождении состояния файл разный | Пишет сервер из единственной копии через `write_with` + `loss_on_save` | Commit серверный, но состояние реплик может разойтись |
| 2. 2–5 участников, 100k+ сущностей | Дёшево по трафику, дорого по риску | Дельта по чанкам, лимит на операцию | Оверхед метаданных на каждое поле |
| 3. Не слать весь документ | Да | Да (дельта) | Да |
| 4. Per-user undo | Нет | Да (инверсии дельт на актора) | Да, но «undo» в CRDT — отдельная проблема |
| 5. Тесты без GUI | Да, но недетерминированы | Да: сервер + N headless-клиентов, детерминированно | Да, но сценариев сходимости много |
| 6. Rust/WASM, разумный объём | Да | Да, средний объём | Нет: свой CRDT-стек |
| 7. Один конверт на 5 приложений | Да | Да (конверт общий, дельта — app-specific) | Да (конверт общий) |

## 4. Рекомендация: вариант B

Рекомендую **B: авторитетный сервер, интент на входе, нормализованная дельта
модели на выходе**. Это единственный вариант, который переживает пункты 1, 2, 7
и 8 из §1 без переизобретения семантики движка.

Конкретно для CADCraft:

**Единица операции.** Одна транзакция = одно пользовательское действие
(команда с финальными параметрами, включая результат drag: `move`, `stretch`,
`rotate` с итоговыми координатами). Конверт:

```json
{ "opId": "c7-000123", "session": "…", "actor": "…", "baseVersion": 41,
  "intent": { "kind": "command", "command": "line",
              "params": { "points": [[0,0],[10,0]] },
              "context": { "space": "model", "layout": null, "mspace": null } } }
```

Ответ/рассылка:

```json
{ "version": 42, "opId": "c7-000123", "actor": "…",
  "changes": [
    { "t": "entity.create", "handle": "2A1", "space": "model",
      "order": { "after": "29F" }, "entity": { … } },
    { "t": "entity.replace", "handle": "1C0", "entity": { … } },
    { "t": "entity.delete", "handle": "305" },
    { "t": "layer.rename", "id": "L-7f3a", "from": "WALLS", "to": "WALLS-2" },
    { "t": "table.order", "id": "L-7f3a", "before": "L-0001" }
  ],
  "notSaved": { "ACAD_PROXY_ENTITY": 2 } }
```

- `intent` — `command` (разрешённый allowlist) или нормализованный op
  (`entity.create/replace/delete`, `table.*`, `layout.*`, `order.*`) для тех
  случаев, где команды нет (например, «переименовать слой» как одна операция,
  а не N правок свойств).
- `changes` — результат серверного исполнения: дифф по чанкам
  (`EntityStore::same_as`/`chunk_slices`) плюс явные табличные операции,
  которые диффом по сущностям не выводятся (переименование, порядок, удаление
  слоя с каскадом).
- Клиент применяет дельту через тот же `Drawing` API и обновляет только
  затронутые чанки индекса/рендера; оптимистичный показ — «карандаш» до
  получения версии, при отказе сервера — откат к `baseVersion`-снимку клиента.

**Почему не A.** Пост-проходы решателя и ассоциативности делают результат
функцией **всего** чертежа. Даже два клиента с одинаковым кодом разойдутся
после первого undo или после правки, применённой в разном порядке. Плюс A не
даёт per-user undo и не мешает viewer'у исполнить команду.

**Почему не C.** См. §2: геометрия — атомарное связанное значение, имена —
идентификаторы, а derived-состояние всё равно требует авторитетного пересчёта.
CRDT добавил бы оффлайн, которого в критериях Phase 0 нет, ценой собственного
CRDT-стека в Rust/WASM.

## 5. Позиции по десяти измерениям

| # | Измерение | Позиция CADCraft | Обоснование (факт) |
|---|---|---|---|
| 1 | Единица операции | **B**: транзакция = пользовательское действие; вход — команда/нормализованный op, выход — дельта модели | Команда — функция над `Session`; пост-проходы `constraints`/`assoc` меняют сущности, которых команда не касалась |
| 2 | Идентификаторы | **А**: серверные `Handle` для сущностей (уже есть, переживают save/load) + сессионный UUID для каждой записи таблицы (слой/стиль/блок/layout), потому что они адресуются именем | `Handle(u64)` из `handseed`; `repoint` при переименовании обходит весь чертёж |
| 3 | Порядок и версии | **B**: один серверный счётчик `version` на чертёж, строгий порядок, идемпотентность по `opId` (повтор возвращает прежний результат); клиент применяет только `v = local+1`, иначе ресинк снапшотом | COW-снапшот `Arc<Drawing>` даёт дешёвый ресинк; undo уже восстанавливает состояние целиком |
| 4 | Конфликты | **B**: оптимистичное применение с `expect` (хэш содержимого/версия затронутых сущностей); при несовпадении сервер применяет к актуальному состоянию и присылает **свой** результат + пометку конфликта, UI сообщает «объект изменён другим участником»; OT/CRDT не нужны, гранулярность — сущность целиком | `EntityStore::modify` заменяет `Arc<Entity>` целиком: посвойственных merge-семантик нет |
| 5 | Снапшоты | **B**: снапшот = DXF-байты `write_with` на версии чертежа (нативный путь, `Unknown`/`foreign` пишутся обратно) + журнал опов после него; compaction по N операций/времени; рестарт = `read(snapshot)` + реплей журнала (handle'ы сохраняются) | `io::read/write`, `handseed` и entity handles переживают round-trip |
| 6 | Presence | **B**: отдельный эфемерный тип сообщений в том же WS, не в журнале; состояние при join + курсор ≤10 Гц; политика «последнее побеждает» с drop при отставании; поле: пространство/лист, точка в WCS, viewport, выбор (handle'ы, ограниченно), активный слой | `Session.cursor`, `DocState.selection`, `views` — всё уже есть в памяти; наружу сейчас отдаётся только запросом |
| 7 | Топология сервера | **B**: один sync-сервис на пять приложений: общий конверт/транспорт/JWT/журнал + per-app «apply adapter»; для CADCraft адаптер — нативный крейт, линкующий `cadcraft-engine` (не WASM: DWG-мост — дочерний процесс) | `crates/dwg` работает через `worker`; WASM-сборка без DWG и без потоков |
| 8 | Auth и lease | **B**: JWT `{sub, fileId, role, sessionId, exp}`; роль проверяется на сервере на **каждую** транзакцию (`viewer` не может писать); одна сессия-комната на файл; отзыв = закрытие комнаты/понижение роли и разрыв WS; продление коротким lease | `Session` не имеет read-only режима — ограничение обязано быть серверным |
| 9 | Commit | **B**: сервер пишет файл сам из авторитетной копии (`write_with`, версия из заголовка/кабинета), **до записи** считает `loss_on_save`, возвращает кабинету `{bytes|upload, notSaved, sha256, version}`; кабинет создаёт новую версию и хранит предыдущую; внешнее изменение файла → `409` по ETag/версии | `loss_on_save`/`notSaved`/`.bak` уже реализованы; `set_deliver` — готовый хук доставки |
| 10 | Offline и undo | **B**: оффлайн-правки в v1 запрещены (оффлайн — только просмотр и presence); per-user undo — стек инверсий на актора (before-образы затронутых сущностей + обратные табличные операции), применяется тем же путём с `expect`, при несовпадении — частичный отказ с отчётом; каскад (удаление слоя) — одна транзакция, ограниченная лимитом | Инверсий в движке нет; снапшот глобальный и на документ |

## 6. Что это значит для реализации (границы Phase 1)

- Новый клиентский транспорт: натив — WebSocket-клиент в `engine`/app,
  WASM — `web-sys::WebSocket`; конверт общий с остальными четырьмя
  приложениями (критерий 7).
- Новый серверный крейт `cadcraft-collab-server` (или режим CLI): комнаты,
  headless `Session` на чертёж, allowlist интентов, дифф по чанкам, журнал,
  снапшоты, presence, commit, метрики. House rules: `unsafe` запрещён,
  `unwrap/expect/panic` запрещены, зависимости — только из allowlist.
- В движке: снятие диффа (`before`/`after` уже есть в `execute`), применение
  дельты, блокировка `viewer`, отключение локального undo для сессионных
  чертежей в пользу серверного per-user undo.
- Ограничение объёма одной операции (например, ≤5000 затронутых сущностей;
  больше — «слишком большая операция, разделите»), стриминг дельты для
  больших каскадов.
- Фича за флагом; одиночный режим и его undo/сохранение не меняются.

## 7. Открытые вопросы к ADR

1. Считать ли commit успешным при непустом `notSaved` (предлагаю: да, с
   флагом и записью в аудит кабинета).
2. Хранить ли снапшот в DXF или в собственном компактном формате (DXF проще,
   проверен round-trip-тестами; свой формат — быстрее, но новый кодек).
3. Разрешать ли `engine.execute`-интенты вне allowlist в режиме «только
   владелец» (риск: команды вроде `purge`, `audit`, `recover` меняют много).
4. Нужен ли совместный LISP/скрипт-канал (сейчас LISP — сессионное состояние,
   в shared-сессии опасен).
