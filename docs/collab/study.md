## 0. Метод и ограничения

Изучение — только чтение кода и документов репозитория. **В этом окружении нет
`cargo`/`rustc`**, поэтому ни одна цифра времени здесь не измерена: всё, что
касается производительности, либо взято из `docs/architecture.md` (там указано,
что и когда мерили), либо помечено как «не измерено». Утверждения о коде — с
`файл:строка` на указанном коммите.

Расхождение с `TASK.md`: задача описывает проект как *early development*. На
самом деле это зрелый (pre-alpha по собственной оценке) редактор v0.17.0:
~261k строк `.rs` в 12 библиотечных крейтах, 3 приложениях и `xtask`
(`find crates apps -name '*.rs' | wc -l`-агрегат; цифры архитектурного дока
ниже — только `src` без inline-тестов), 422 конструктора `CommandSpec` в
`*::specs()`, 3496 `#[test]` в `crates/`. Ограничения из `TASK.md`
(немоделируемые сущности теряются при записи) подтверждаются и уточняются в §5.

## 2. Модель документа

Корень — `Drawing` (`crates/doc/src/lib.rs:95`):

```rust
pub struct Drawing {
    pub header: Header,
    pub foreign: Arc<foreign::Foreign>,   // данные файла, которые не моделируются
    pub layers: Vec<Layer>,
    pub linetypes: Vec<Linetype>,
    pub text_styles: Vec<TextStyle>,
    pub dim_styles: Vec<DimStyle>,
    pub mleader_styles: Vec<MLeaderStyle>,
    pub table_styles: Vec<TableStyle>,
    pub mline_styles: Vec<MLineStyle>,
    pub blocks: BTreeMap<String, Arc<Block>>,
    pub model: EntityStore,
    pub layouts: Vec<Layout>,             // у каждого свой EntityStore (paper space)
    pub active_layout: Option<String>,
    pub views / vports / ucss / layer_states / groups / plot_style_tables / scales,
    pub constraints: Vec<Constraint>,
    pub handseed: u64,                    // следующий свободный handle
    // сессионное, не пишется в файл:
    pub hidden_objects: BTreeSet<Handle>, pub read_notes: Vec<String>,
    pub refedit: Option<RefEdit>, pub skipped_records: …,
}
```

- **Сущности.** `Entity { handle: Handle, common: Common, kind: EntityKind }`
  (`crates/doc/src/entity.rs:13`). 31 вариант `EntityKind` (`entity.rs:72`): линии,
  окружности, дуги, эллипсы, LWPOLYLINE, 3D POLYLINE, SPLINE, HELIX, RAY/XLINE,
  TEXT/MTEXT, ATTDEF, INSERT (с атрибутами), DIMENSION (7 видов), MLINE, LEADER,
  MLEADER, HATCH, SOLID, TRACE, 3DFACE, POLYFACE, REGION, VIEWPORT, IMAGE,
  WIPEOUT, ACAD_TABLE, TOLERANCE, `Unknown` (сырые DXF-теги).
- **Хранилище.** `EntityStore` (`crates/doc/src/store.rs:22`) — copy-on-write:
  сущности лежат в чанках `Arc<Chunk>` по ≤1024 (CHUNK_MAX) в порядке отрисовки,
  плюс 64 шаpда индекса `HashMap<Handle, chunk_id>`. Клон хранилища копирует
  только указатели, правка копирует **один** чанк и **один** шард.
- **Порядок отрисовки** — это позиция в `EntityStore`, а не отдельное поле;
  `push`/`push_front`/`bring_to_front`/`send_to_back` двигают её физически.
- **Таблицы имён** (`layers`, `linetypes`, `*_styles`, `layouts`, `groups`,
  `layer_states`) — `Vec` с именами; `block` — `BTreeMap<String, Arc<Block>>`.
  Имена ищутся регистронезависимо (`Drawing::layer`, `lib.rs:227`).
- **Пространства.** `Space::Model | Space::Paper(layout_name)` (`lib.rs:51`).
  `Drawing::space_of(handle)` ищет сначала в модели, потом в layouts (`lib.rs:351`) —
  handle уникален на весь чертёж, включая листы.
- **Блоки.** `Block` (`crates/doc/src/tables.rs:691`): имя, база, свой
  `EntityStore`, `anonymous` (сгенерированные `*D`/`*U`), `xref_path`,
  `array`. `INSERT` ссылается на блок **по имени**.
- **Размеры.** `Dimension` хранит геометрию и `block: Option<String>` — блок
  `*D` при записи **генерируется** из размеров (`crates/io/src/dxf_write/blocks.rs:19`),
  как и блок `*T` таблицы. То есть геометрия размера/таблицы — производная, в
  операции её везти не нужно.
- **Чужие данные.** `foreign::Foreign` (`crates/doc/src/foreign.rs:1`) хранит
  объекты, CLASS-записи, xdata, extension dictionaries, reactors, data store
  ACIS «как есть» и пишет их обратно; команды их не редактируют.

### Стабильные ID: что есть

| Узел | Идентификатор | Устойчивость |
|---|---|---|
| Сущность (любое пространство, блок) | `Handle(u64)` = DXF group 5, глобально уникален в чертеже | Выдаётся `Drawing::new_handle()` из `handseed` (`lib.rs:213`). **Сохраняется** при записи/чтении своих файлов (entity handles kept, `docs/gaps.md` FF7). Не меняется при undo/redo (снапшот возвращает тот же объект). |
| Слой, тип линии, стиль, layout, группа, состояние слоёв | имя (строка, case-insensitive) | Меняется пользователем; переименование — глобальный каскад (§6). |
| Блок | имя в `BTreeMap` | Переименование — каскад по всем ссылкам (`cmd/props/rename.rs:21`). Анонимные блоки имя не меняют. |
| VIEWPORT | `Viewport.id: u32` (DXF id) + handle сущности | `id` — из файла, может дублироваться; для адресации годится только handle. |
| Dimension ↔ объекты | `Dimension::assoc` → `DimAssoc { handle, snap }` | Ссылки на handle; при удалении объекта ассоциативность рвётся. |

Вывод: **пространство сущностей уже имеет стабильные ID** (handle), и оно
переживает save/load CADCraft-файлов. Таблицы имён — нет: у слоя/блока/стиля
нет сущности-ID, только имя, а имя — редактируемое поле. Для сессии нужен
отдельный ID записи таблицы (UUID на имя), иначе «переименование слоя» и
«правка сущности на этом слое» неразрешимы по порядку.

## 3. Команды и мутации

- Правка идёт только через команды, но команда — **не данные, а функция**:
  `CommandSpec { id, label, menu, shortcut, aliases, params: &'static str,
  enabled: fn(&Session)->Result<(),String>, run: fn(&mut Session,&Value)->Result<Value>,
  undoable, interactive, transparent }` (`crates/engine/src/cmd.rs:69`).
  Реестр собирается в `command_specs()` (`:175`) из `*::specs()`; в исходниках
  422 конструктора (архитектурный док на 2026-10-10 называет 295
  зарегистрированных и 128 с интерактивными промптами — репозиторий с тех пор
  вырос).
- Программный вызов: `Session::execute(id, params)` (`session/execute.rs:11`).
  Параметры — `serde_json::Value`; JSON-форма **никогда** не открывает диалоги,
  все интерактивные ветки — отдельный `Factory` (машина промптов).
- Параметры сериализуемы, но **эффект команды — произвольный Rust над `&mut
  Session`**. Команда читает и пишет состояние сессии: активное пространство
  (`DocState::space`), системные переменные и `CLAYER` из header, текущий выбор
  (`has_selection`), `last_used`, буфер обмена, LISP-состояние, счётчики
  `untitled_counter`. Пример: `document.bytes`, `entities` и `drawing.inspect` —
  тоже команды.
- **Пост-проходы после каждой undoable-команды** (`session/interactive.rs:416`):
  1. `cmd::groups::after_command`,
  2. `cmd::constraints::after_command` (`cmd/constraints.rs:1136`) — запускает
     параметрический решатель по всему чертежу и может **сдвинуть сущности,
     которых команда не касалась**;
  3. `assoc::after_command` (`assoc.rs:402` → `update`, `assoc.rs:357`) —
     двигает определяющие точки ассоциативных размеров.
  То есть одна команда может изменить неограниченное множество сущностей, и
  результат зависит от всего состояния чертежа и от порядка применения.
- Защита от нечисловых результатов: `refuse_non_finite` (`finite.rs:1`)
  откатывает чертёж, если после команды у изменённого объекта NaN/inf.

**Следствие для протокола.** «Команда как единица операции» (id + params)
непригодна: получатель не сможет воспроизвести эффект, не имея ни того же
`Session`, ни того же порядка пост-проходов. Единицей операции должен быть
**нормализованный набор изменений модели**, вычисленный на авторитетной стороне.

## 4. Undo/redo

- Стек — на документ: `DocState { doc: Arc<Drawing>, undo: Vec<Snapshot>,
  redo: Vec<Snapshot>, undo_ctl, selection, revision, … }`
  (`crates/engine/src/doc_state.rs:13`).
- `Snapshot { label: String, doc: Arc<Drawing>, selection: Vec<Handle> }`
  (`doc_state.rs:5`). До команды сохраняется текущий `Arc<Drawing>`, после изменения
  он кладётся в стек — `push_undo` (`session/execute.rs:81`): клон `Arc` не копирует
  сущности (COW), но первая мутация после снапшота клонирует саму структуру `Drawing`
  (`Arc::make_mut`, `engine/src/lib.rs:223`), включая `Vec<Layer>`/`Vec<Layout>`.
- `undo()`/`redo()` меняют местами текущий и снятый чертёж, восстанавливая и
  выбор (`execute.rs:102`, `doc_state.rs:80`). Метки шагов — человеческие
  (label команды); `UNDOCTL`/`BEGIN`/`END` группируют шаги (`engine/src/undoctl.rs`),
  LISP-рутина — один шаг.
- Стек **глобальный на чертёж**, не на пользователя; инверсий команд нет;
  снапшот несериализуем (в нём `Arc<Drawing>` и `EntityStore` с `#[serde(skip)]`).
- Память шага ≈ копия структуры `Drawing` (таблицы имён и layouts — десятки-сотни КБ
  при сотнях слоёв/блоков) + изменённый чанк (≤1024 сущности) + один шард индекса,
  а не весь чертёж. Это делает снапшоты дешёвыми локально — и **непригодными** для
  отправки по сети и для per-user undo в исходном виде.
- Для диффа состояний есть готовый примитив: `EntityStore::same_as`
  (сравнение по указателям чанков, `store.rs:271`) и `chunk_slices()`
  (`store.rs:277`) — позволяют пройти только изменённые чанки. В `crates/io`
  есть полноценный `roundtrip::compare` (по handle, категориям и допускам),
  но он рассчитан на файловый round-trip, а не на горячий путь.

## 5. Сериализация и round-trip

- Чтение: `cadcraft_io::read(bytes, name)` (`crates/io/src/lib.rs:77`) —
  формат по содержимому: DXF (свой парсер `crates/dxf`), DWG (мост
  `acadrust`, `crates/dwg`), SVG/SVGZ.
- Запись: `write`/`write_with` (`io/src/lib.rs:102`) — DXF ASCII/binary,
  версии 2000–2018 (по умолчанию 2018), DWG — через тот же мост (не ниже 2004).
  R12 на запись нет, R12 binary на чтение нет; WASM не умеет DWG.
- **DWG-мост работает в дочернем процессе** (`cadcraft_dwg::worker`,
  `io/src/lib.rs:65`) — падение конвертера не роняет приложение. Для сервера
  это означает: commit в DWG требует нативного процесса с форком, не WASM и не
  «чистого» async-рантайма.
- **Что не моделируется.** Два механизма: `EntityKind::Unknown` (неизвестные
  типы сущностей с сырыми тегами) и `foreign::Foreign` (объекты, CLASS, xdata,
  extension dictionaries, reactors, ACDSDATA). DXF пишет их обратно (#528) отдельным raw-проходом
  (`dxf_raw::finish`, `io/src/dxf_write/sections.rs:1147`; обычный писатель
  сущностей такие типы пропускает — `io/src/dxf_write/entity.rs:768`),
  насколько может; DWG-мост теряет кастомные классы, объекты и часть foreign
  данных (`docs/gaps.md` top-10 №1, FF1; `cadcraft::cmd::file::drops_unknown`,
  `loss_on_save`, `cmd/file.rs:835`).
- **Предупреждение уже реализовано**: `loss_on_save()` считает, что будет
  потеряно, **до** записи, а `not_saved_message()`/`report_not_saved()` отдают
  список в результат (`notSaved`) и в командную строку; интерактивный QSAVE
  спрашивает и делает `.bak`. Кабинету это даёт готовый API для
  «сохранить версию → показать предупреждение».
- **Что не попадает в файл вообще** (сессионное): `hidden_objects`, `refedit`,
  `read_notes`, `skipped_records`, `rasters`, рендеринг-кэши. Снапшот сервера,
  собранный из DXF, эти поля не восстановит — для collab-сессии их и не надо
  синхронизировать, но надо помнить при восстановлении после рестарта
  (изоляция объектов на клиенте не переживёт reconnect и не должна).
- **Round-trip без правок.** Проверяется harness'ом `crates/io/src/roundtrip.rs`
  (`compare` по handle и категориям) на синтетических файлах; реального корпуса
  нет (FF5), в AutoCAD вывод не проверялся (top-10 №2). Для collab это значит:
  commit не может обещать «идентичный файл», только «в рамках модели CADCraft».

## 6. Структурные правки и их цена

| Операция | Что ломается при конкурентной правке | Цена / особенности |
|---|---|---|
| Создать сущность | Два клиента выдали один handle (если ID клиентские) | Серверный `new_handle` из `handseed` — единственный безопасный вариант; `Drawing::add` сам зовёт `new_handle` (`lib.rs:368`) |
| Изменить сущность | Два клиента правят одну сущность или соседние свойства | `EntityStore::modify` заменяет весь `Arc<Entity>`; гранулярность — сущность целиком, посвойственных merge нет |
| Удалить сущность | Другой клиент уже изменил её; размер/ассоциативность на неё ссылаются | `remove` + ассоциативные размеры «повисают»; группы (`Group::members`) и `viewport.clip` держат handle — нужен каскад или tombstone |
| Слой: создать | — | дёшево; имя должно быть уникально case-insensitive |
| Слой: переименовать | Сущности на слое ссылаются на имя; вложенные блоки и листы тоже | `rename.rs:21 repoint()` проходит **все** хранилища: модель, все layouts и все определения блоков; при 200k сущностей это полный проход. Должно быть одной операцией, а не N правок свойств |
| Слой: удалить (`laydel`) | Кто-то рисует на этом слое прямо сейчас | `cmd/layer/merge.rs:191`: удаляет **все** объекты на слое во всех пространствах и блоках + чистит заморозки во вьюпортах; слой «0»/Defpoints/текущий защищены. Огромный каскад |
| Блок: определить/переопределить | Два клиента правят один блок; ссылки видят разное | `Block` за `Arc`, правка через `Arc::make_mut`; переопределение меняет вид всех `INSERT` сразу |
| Блок: переименовать | INSERT ссылается по имени | каскад по `Insert::block` и `MLeader::block` (`rename.rs:24+`) |
| Лист (layout): создать/удалить | Активный layout у другого клиента | `active_layout` — имя; удаление листа уносит его `EntityStore`; `DocState::follow_layout` умеет пережить переименование/удаление (`doc_state.rs:80,90`) |
| Вьюпорт | `clip: Option<Handle>` ссылается на объект листа; `frozen_layers` — на имена слоёв | межпространственная ссылка: удаление объекта-клипа ломает вьюпорт |
| Размер | Ассоциативные точки ссылаются на handle геометрии | геометрия `*D` — производная (генерируется при записи); при правке геометрии пост-проход `assoc` двигает размер |
| Штриховка | Ассоциативная граница + реактор | при удалении границы штриховка остаётся «висячей» |
| Таблица | `*T` — производный блок; формулы CADCraft-специфичны | правка ячейки — это правка сущности `Table`, блок пересобирается при записи |
| Порядок отрисовки | Позиция в списке, а не поле | вставка/удаление двигает индексы; для операции нужен якорь (before/after handle), а не числовой индекс |
| Параметрические ограничения | Решатель глобальный и порядко-зависимый | `constraints::after_command` может двигать много сущностей; два клиента, меняющие связанную геометрию, получат разные результаты при локальном пересчёте |
| Xref | `xref_path`, `xref_status` — сессионные/файловые | внешние файлы не входят в документ; совместное редактирование xref — вне области |

**Цена пересчёта.** `render::build` строит display list заново на каждое
изменение пространства; на нативе тесселяция параллелится через rayon, на
WASM — нет (`crates/render/src/pipeline.rs:146`). R-tree переиндексирует только
изменённый чанк: индекс кэшируется по идентичности содержимого
(`crates/engine/src/spatial.rs:1`), пространства <256 сущностей сканируются
напрямую (`spatial.rs:24`). `docs/architecture.md` утверждает «picking ≈0.001 ms
at 200k entities» и «display list once per change»; **сам я это не мерил** —
в репозитории есть готовый стенд `cadcraft-cli perf` (`apps/cadcraft-cli/src/perf.rs`),
который печатает построение display list, pick, osnap, DXF read/write на
синтетических 200k сущностей и на файле.

## 7. Существующие хуки для collab

Есть:

- `Session::execute(id, params)` — единственная программная точка выполнения
  любой команды; `catch_unwind` + откат при панике (`guard.rs`).
- `Session::after_command` — место, куда уже встроены глобальные пост-проходы;
  сюда же логично встроить «снять дифф после применения чужой операции».
- `DocState.revision` (растёт на каждое изменение) и `DocState::is_dirty` —
  готовые сигналы «что-то изменилось», но без «что именно».
- Контрольный канал: JSON-lines поверх loopback TCP, per-session token из
  файла в runtime-dir, лимиты соединений/очереди/размера
  (`docs/control-protocol.md`). **Только request/response** — push-событий и
  подписок нет.
- MCP-сервер (`cadcraft-cli mcp`, `--connect HOST:PORT`) — обёртка над тем же
  протоколом; headless-сессия в процессе.
- `cmd::file::set_deliver` — хук доставки сохранённого файла; им пользуется
  web-хост-мост (`apps/cadcraft-web/src/host.rs`), чтобы отдать файл странице
  вместо скачивания.
- Web: `?host=parent`/`data-host="page"`, сообщения `cadcraft:ready/open/save/dirty/failed`
  через общий `craft-web-host` (storytold/craft-libs) — тот же контракт, что у
  четырёх соседних приложений. Это готовое место для `session/presence/commit`.
- Атомарная запись (`engine/src/atomic_write.rs`), autosave/`.bak`
  (`autosave.rs`, QSAVE), `AUDIT`/`RECOVER` (`audit.rs`) — инфраструктура
  версионности уже есть локально.

Нет (придётся добавить):

- никакой сети: прямых зависимостей с `tokio` или WebSocket-крейтом нет
  (`grep websocket/tokio` по всем `Cargo.toml` пуст; `tokio` есть в `Cargo.lock`
  только транзитивно, через `wasm-bindgen-futures`, и не используется) —
  транспорт нужен новый,
  отдельно для натива и для WASM (`web-sys::WebSocket`);
- нет журнала операций, нет push-канала, нет понятия «чужое изменение»;
- нет проверки ролей: `viewer` можно реализовать только снаружи движка
  (обёртка над `execute`), режим «только чтение» в `Session` отсутствует;
- нет presence: `Session.cursor`, `DocState.selection` и `views` есть, но
  наружу отдаются только через запрос (`ui.inspect`, `drawing.inspect`).

## 8. Производительность

- Типичный документ: `examples/apartment.dxf` — 47.6 KiB; число сущностей не
  померил (нет тулчейна). Стенд `perf` умеет генерировать 1k…200k сущностей.
- **Не измерено**: время `render::build`, DXF write/read, стоимость
  снапшота/диффа, стоимость полного прохода `laydel`/`repoint`. Все цифры в
  `docs/architecture.md`/`gaps.md` — авторские оценки, не мои.
- Известные из `gaps.md` ограничения: DWG 10 МБ падал за ~2 минуты (#57, FF6);
  лимиты на размер входных данных и рекурсию блоков (`MAX_BLOCK_DEPTH`).
- **WASM**: сборка ~13 МБ (~5 МБ gzip, `INTEGRATION.md`); rayon выключен,
  потоки не гарантированы; DWG недоступен; всё, что делает сервер синхронизации
  (мост DWG в дочернем процессе, файловые снапшоты), живёт вне браузера.
  Браузерный клиент обязан быть неблокирующим и работать в кадре egui.

## 9. Три варианта протокола (кратко)

| Вариант | Механизм | Плюсы для CADCraft | Минусы | Риск |
|---|---|---|---|---|
| A | **Реплей команд**: `engine.execute(id, params)` на сервере, клиентам уходит id+params, каждый исполняет локально | Максимум переиспользования: 422 команды уже есть, nothing to design | Пост-проходы (решатель, assoc, groups) и состояние `Session` делают результат порядко-зависимым; undo и роли не решаются; viewer может исполнить команду | Высокий: расхождение чертежей без ошибки |
| B | **Серверный нормализованный op + дельта сущностей**: клиент присылает намерение, сервер применяет его через `Session`, сравнивает состояния по чанкам (`same_as`/`chunk_slices`) и рассылает create/replace/delete/order/table-ops с версией | Совпадает с COW-моделью и handle-ID; derived-геометрия остаётся локальной; per-user undo = инверсии дельт; роли и лимиты — на сервере | Нужен свой словарь операций и диффер; чужие правки видны только после сервера (RTT) | Средний: объём проектирования умеренный, сходимость тривиальна (одна авторитетная копия) |
| C | **CRDT по полям сущностей** (LWW-register на свойство, OR-set на коллекции, Yrs/Automerge-подобное) | Оффлайн и P2P «из коробки», нет RTT на правку | Геометрия и таблицы имён — именованные ссылки, derived-блоки и глобальный решатель ограничений в CRDT не выражаются; снапшот/commit всё равно серверные; тяжело для Rust/WASM и house rules (panic-free, свой код) | Высокий: большая поверхность, конфликты имён и порядка отрисовки остаются |

Рекомендация и обоснование — в `options.md`.

## 10. Риски и открытые вопросы

1. **Потеря немоделируемых данных при commit.** DXF пишет `Unknown`/`foreign`
   обратно, DWG — нет. Кабинет обязан хранить предыдущую версию и показывать
   `notSaved`; сервер не должен молча перезаписывать файл. Вопрос к ADR по
   commit: считается ли версия «успешной», если `notSaved` непуст (предлагаю:
   да, но с флагом в ответе и записью в аудит).
2. **Единицы и точность.** Геометрия — f64 в единицах чертежа; `LUNITS/LUPREC`
   только форматирование (`engine/src/units.rs`), `INSUNITS` — метаданные
   чертежа, геометрия по ним не пересчитывается; допусков нет. Значит, по сети
   надо возить точные f64 (`serde_json` собран с `float_roundtrip`), а не
   округлять «для компактности»: округление даст разную геометрию у клиентов.
3. **Порядок отрисовки.** Позиция в списке. Числовой индекс нестабилен при
   параллельных вставках; нужен якорь (before/after handle) или серверная
   нумерация.
4. **Имена как идентификаторы.** Переименование слоя/блока/стиля — глобальный
   каскад. Нужен ID записи таблицы и операция «переименовать», а не N правок.
5. **Derived-состояние.** `*D`/`*T` блоки, ассоциативные размеры, решатель
   ограничений, штриховки-реакторы: либо всё считается на сервере и
   рассылается как данные, либо результат разойдётся. Это главный аргумент
   против реплея команд и против CRDT «по полям».
6. **Viewer.** В движке нет read-only режима. Проверка прав — только на
   сервере + запрет в клиенте (не отправлять намерения); UI-запрет недостаточен.
7. **Большие чертежи.** 200k сущностей: полный дифф — O(n), поэтому дифф
   обязан быть по чанкам; операция над слоем/удалением — O(all), значит нужен
   лимит на размер одной операции и стриминг результата.
8. **Коммит и версии.** CADCraft уже умеет `.bak`, атомарную запись, выбор
   версии DXF/DWG и `loss_on_save`; commit должен переиспользовать это, а не
   писать файл «как получится».
9. **WASM-клиент.** Нет DWG, нет потоков, всё в кадре: транспорт и применение
   дельт должны быть инкрементальными и не блокировать UI.
10. **House rules.** Серверный крейт обязан жить по тем же правилам, что и
    остальные: `unsafe_code = "forbid"`, `deny(unwrap_used, expect_used, panic, …)`,
    лицензии зависимостей — только из allowlist, CI в feature-PR не меняется.
