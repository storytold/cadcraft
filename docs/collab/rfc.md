# RFC: совместное редактирование CADCraft (DXF/DWG)

- Статус: Accepted (кворум 4/5, 2026-11-08, ADR-0014; ядро реализовано и
  покрыто тестами — см. «Состояние реализации»)
- Автор: cadcraft/envoy
- ADR: `bus/decisions/0001-op-unit.md` … `0014-rfc-accepted.md` (все accepted),
  сводка — `.craft/protocol/ARCHITECTURE.md`. Уточнения общего конверта:
  ADR-0012 (`epoch` — поколение позиционных адресов; CAD его не использует) и
  ADR-0013 (чанкованная дельта `applied`).
- Upstream issue/PR: PR в `storytold/cadcraft` открывается после принятия RFC
  (house rules: `main` — через PR, CI в feature-PR не меняется). RFC принят,
  ветки и описания PR готовятся без пуша.
- Основание: `upstream/docs/collab/study.md`, `options.md` (коммит `441e4925`),
  upstream `a655cee0`

## 1. Контекст

CADCraft сейчас — одиночный редактор: один пользователь, один чертёж, одна
сессия. Правка идёт командами (`CommandSpec::run: fn(&mut Session, &Value)`,
`crates/engine/src/cmd.rs:69`), после каждой undoable-команды движок делает
глобальные пост-проходы — параметрический решатель (`cmd/constraints.rs:1136`),
ассоциативные размеры (`assoc.rs:402`), группы — и может изменить сущности,
которых команда не касалась. Undo — снапшот всего `Arc<Drawing>` на документ
(`doc_state.rs:5`), без автора и инверсий. Сети в проекте нет: ни одной прямой
зависимости с `tokio`/WebSocket; web-сборка общается с кабинетом через
`craft-web-host` (`apps/cadcraft-web/src/host.rs`).

Главное ограничение проекта: **DXF пишет обратно то, что не моделируется**
(`Unknown` + `foreign`, raw-проход `dxf_raw::finish`), а **DWG-мост теряет часть
этих данных**; `loss_on_save` (`cmd/file.rs:835`) уже считает потери до записи.
Поэтому commit обязан нести `notSaved`, а кабинет — хранить предыдущую версию.

## 2. Цели и не-цели

**Цели.** Совместное редактирование одного чертежа 2–5 участниками в реальном
времени: сущности, слои, блоки, размеры, штриховки, листы и вьюпорты; presence;
роли; per-user undo; commit в `.dxf`/`.dwg` с новой версией в кабинете.

**Не-цели.** Оффлайн-редактирование, CRDT/OT, совместная работа с разными
чертежами, полная совместимость с AutoCAD, изменение поведения одиночного
режима, 3D.

## 3. Модель данных для синхронизации

**Документ на сервере.** Авторитетная копия — `cadcraft_engine::Session` с одним
`Drawing` и фиксированным контекстом (активное пространство приходит в операции,
а не берётся из окна). Состояние сессии = **снапшот (DXF-байты) + хвост журнала**
(ADR-0005). DXF-снапшот сохраняет непромоделированные части, потому что писатель
возвращает их raw-проходом; DWG в снапшот не идёт.

**Единица операции (ADR-0001).** Транзакция одного пользовательского действия:

```
op = { opId, sessionId, actor, baseVersion, kind, payload, context }
kind ∈ "command" | "primitive" | "structural"
context = { space: "model" | "paper", layout?: string, mspace?: handle,
            selection?: [handle], clay?: string }
```

**Слой автора (`clay`, ADR-0019).** Операция, создающая объекты, называет в
контексте слой, на котором рисовал автор, — имя текущего слоя его реплики
(`CLAYER`). Без этого сервер создал бы объект на своём `CLAYER`: сервер не
знает, какой слой выбрал участник, и `drawing.header` в дельту не входит (слои
синхронизируются только как записи таблицы, §3). Правила:

- имя разрешается по таблице слоёв авторитетного чертежа и дальше едет в
  написании чертежа, чтобы все реплики получили одинаковые байты;
- слой, которого в чертеже нет (в том числе слой, существующий только в
  реплике автора), отклоняется **до** исполнения команды: `rejected{code:
  "invalid"}`, документ и `version` не меняются;
- слой — часть операции, а не настройка сессии: `CLAYER` сервера и
  получателей не меняется, дельта несёт только `entity.create` с
  `entity.common.layer`;
- у получателя объект применяется в слой из дельты (`apply` проверяет
  существование слоя до вставки и отвечает `no such layer`, если таблица
  разошлась — тогда нужен ресинк);
- undo шага возвращает то, что слой держал до шага; `handseed` остаётся
  впереди, handle не переиспользуется (ADR-0002).

Проверено срезом §6 п.1 (`feat/collab-cmdline`, head `9916fb92`): две реплики
с разными слоями рисуют `line`/`polyline`, сходятся, каждый видит объект в слое
автора, а свой текущий слой сохраняет; viewer получает `forbidden`;
неадресуемый слой не мутирует документ.

**Автор и id операции — не поля клиента.** `actor` и `sessionId` в конверте
информативные: сервер **игнорирует** присланные значения, берёт автора из
проверенного JWT (`sub`), а сессию — из соединения (`welcome.sessionId`);
`applied.actorId` — всегда результат проверки токена, а не эхо клиента. Иначе
клиент подписал бы правку чужим именем (замечание pdfcraft
`20261108T103023Z-pdfcraft-2193`, ADR-0008). `opId` формирует клиент как
`clientId:seq`: `clientId` приходит в `welcome`, `seq` — монотонный счётчик,
который не сбрасывается при reconnect; сервер `opId` не перегенерирует, а
использует как ключ дедупа (§4.3).

- `kind:"command"` — id команды + JSON-параметры (форма `engine.execute`), но
  адреса явные: `space`/`layout`, выбранные handle'ы, а не состояние окна.
- `kind:"primitive"` — нормализованная операция там, где команды нет или где
  нужна одна атомарная единица: `table.rename`, `table.delete`, `layout.create`,
  `order.move`, `entity.group.*`.
- `kind:"structural"` — операция, чей результат зависит от других объектов
  (каскад): удаление/переименование слоя, переопределение блока, удаление листа,
  удаление сущности со ссылками.

**Ответ (ADR-0001, 0003).** Авторитетный результат: `version`, подтверждённая
операция и **дельта модели**:

```
changes = [
  {t:"entity.create", handle, space, order:{after|before|bottom|top}, entity},
  {t:"entity.replace", handle, entity},
  {t:"entity.delete", handle},
  {t:"entity.order", handle, order},
  {t:"table.create|table.update|table.rename|table.delete", recordId, kind, …},
  {t:"layout.create|layout.rename|layout.delete", recordId, …},
  {t:"block.create", name, properties, entities},
  {t:"block.delete", name},
  {t:"drawing.header", key, value}
]
```

**Блоки едут целиком (ADR-0020).** Объекты блока живут в `Block::entities`, а не
в пространстве, поэтому дельта сущностей их не несёт: реплика, получившая
только ссылку (`entity.create` с `Insert`), нарисовала бы пустоту. Поэтому
`diff_all` сравнивает таблицу блоков (`Arc::ptr_eq`, затем содержимое) и шлёт
`block.create` — свойства определения плюс его объекты в порядке отрисовки —
до изменений сущностей, а `block.delete` — когда определение исчезло. Так undo
создания блока снимает определение и на репликах, а redo возвращает его.
Внутренние handle блока выдаёт сервер; получатель поднимает `handseed`
(ADR-0002).

Производное не едет: анонимные блоки `*D`/`*T`, которые CADCraft генерирует
при записи DXF, в дельту не входят; блоки, созданные командой в сессии, —
входят (см. выше).

**Идентификаторы (ADR-0002).**
- Сущность — `Handle(u64)`, выдаёт сервер из `handseed`; он стабилен и переживает
  save/load, поэтому в дельте едет handle.
- Запись таблицы имён (`layer`, `linetype`, `text/dim/mleader/table/mline style`,
  `layout`, `group`, `layer state`) — `recordId` (UUID), выдаётся на сессию;
  имя — изменяемое значение, не ключ. Сервер ведёт карту `recordId ↔ имя`.
  Без этого переименование слоя выглядело бы как удаление + создание.
- Порядок отрисовки — позиция в `EntityStore`, поэтому в дельте он адресуется
  якорем (`after`/`before`/`top`/`bottom` по handle), а не индексом.
- Надгробия: удалённый `recordId`/`handle` не переиспользуется в сессии;
  операция по удалённому адресу отклоняется (`retryable:false`).
- **Позиционные адреса и `epoch` (ADR-0012).** В CAD адрес — `Handle`/`recordId`,
  а не индекс: structural-правка (удаление слоя, листа, перестановка порядка)
  адреса не сдвигает, поэтому `epoch` не нужен — осознанное отличие от PDF,
  Grid, Word и Deck, где `epoch` обязателен. От повторов защищает `version`/
  `baseVersion` и дедуп `opId` (§4.3).

## 4. Протокол

### 4.1 Транспорт

WSS, один канал на комнату `(fileId, app="cadcraft")`. Фрейм — JSON (UTF-8),
лимит 1 MiB на сообщение; дельта больше 1 MiB дробится на несколько `applied` с `more:true`
с флагом `more:true` (см. §4.4). Presence — ≤2 KiB. Бинарные фреймы не нужны:
геометрия — f64 в JSON (`serde_json` с `float_roundtrip` у обеих сторон).
Native-клиент — Rust WebSocket; WASM — `web-sys::WebSocket`, всё в кадре egui,
без блокирующих вызовов.

### 4.2 Сообщения

Имена и поля — по общему конверту `.craft/protocol/ARCHITECTURE.md` §2: `hello`,
`welcome`, `op`, `undo`, `redo`, `applied`, `rejected`, `presence`, `resync`,
`snapshot`, `commit`, `commit-result`, `error`, `ping`/`pong`. Приложение
уточняет только тело `target`/`payload` и `result`.

| Тип | Направление | Поля | Семантика |
|---|---|---|---|
| `hello` | C→S | `{app:"cadcraft", doc, jwt, client{name,ver}, lastVersion?}` | JWT первым сообщением, не в URL (ADR-0008) |
| `welcome` | S→C | `{sessionId, actorId, role, lease, version, participants[], capabilities, snapshot?}` | `snapshot` — ссылка на базу, если `lastVersion` вытеснен |
| `op` | C→S | `{opId, baseVersion, kind, target, payload, preview?}` | намерение; `target` несёт `space`/`layout`/`selection` (§3) |
| `undo` | C→S | `{opId}` | отменить последнюю операцию участника; ответ — `applied` или `rejected{code:"undo-conflict"}`; это не `op` с командой `undo`, а отдельное сообщение конверта |
| `redo` | C→S | `{opId}` | вернуть последнюю отменённую операцию; ответ — `applied` или `rejected{code:"redo-conflict"}` |
| `applied` | S→C | `{opId, version, actorId, result:{command?|delta?|both}, more?}` | авторитетный результат: автору — `command`, остальным — `delta`; длинная дельта дробится с `more:true` |
| `rejected` | S→C | `{opId, code, message, retryable, hint?}` | отказ (`stale|conflict|forbidden|invalid|auth|lease`) |
| `presence` | C↔S | `{space, layout, cursor:[x,y], viewport, selection[], layer, mspace}` | не журналируется, без подтверждений |
| `resync` | C→S | `{lastVersion}` | догон или база + хвост |
| `snapshot` | S→C | `{version, seq, more, bytesBase64, sha256}` | чанки по 1 MiB (`seq` с 0, `more` у всех кроме последнего); клиент сбрасывает непринятую очередь |
| `commit` | C→S | `{expectedVersion}` | запрос сборки файла (ADR-0009) |
| `commit-result` | S→C | `{version, sha256, bytes?, notSaved, path?}` | результат commit |
| `error` | S→C | `{code, message, retryable}` | общие ошибки (auth, lease, лимиты) |
| `ping`/`pong` | C↔S | `{}` | lease продлевается `ping` |

Отклонение от общего конверта одно и записано явно: `snapshot` чанкуется по
1 MiB, потому что DXF на 100 MB в base64 — это ~133 MB одним сообщением
(замечание gridcraft к ревью `rfc/cadcraft`).

### 4.3 Порядок и версии (ADR-0003)

- Один монотонный `version` на чертёж, без пропусков; увеличивается каждой
  принятой операцией (`presence` не увеличивает).
- `opId = clientId:seq` (формирует клиент, §3); окно идемпотентности ≥24 ч
  или ≥10 000 операций. Повтор возвращает сохранённый `applied`, операция
  **не исполняется второй раз** (иначе повторно выделятся handle и сработают
  пост-проходы).
- `baseVersion` — контекст. `kind:"structural"` требует `baseVersion == head`
  и исполняется в эксклюзивной секции; остальные применяются к head.
- Клиент применяет `applied` только при `version = local+1`; иначе
  `snapshot` и сброс очереди.
- Чанки одной дельты идут подряд и не перемежаются чужими `applied`: версия
  фиксируется на первом чанке, клиент применяет документ только после
  `more:false`, а следующие сообщения ждут. Иначе клиент получил бы половину
  версии N, сверху версию N+1 и другое состояние. Это правила 1–3 ADR-0013;
  остальные: лимит 8 MiB на дельту при 1 MiB на сообщение (превышение —
  `rejected{code:"invalid"}` до рассылки), а `resync{from}` после обрыва в
  середине чанков переигрывается с `lastVersion`, до первого чанка, а не с
  середины (правила 5–6).

### 4.4 Конфликты (ADR-0004)

| Ситуация | Политика | Что видит пользователь |
|---|---|---|
| Двое правят разные сущности | обе применяются по порядку сервера | обе правки |
| Двое правят одну сущность | вторая применяется к head, ответ несёт `conflict:true`; правка атомарна (вся сущность) | «объект изменён другим участником», новая версия объекта |
| Двое правят свойства одной сущности (слой, цвет) | то же: сервер применяет к head, `conflict:true` | как выше |
| `structural` при устаревшем `baseVersion` | `rejected{code:"stale", retryable:false}`; структурные операции стоят в **серверной FIFO-очереди**, клиент ждёт `applied`, а не повторяет (иначе две структурные операции отбивают друг друга) | «структурная операция ждёт своей очереди» |
| Операция по удалённой сущности/слою | `rejected{code:"gone", retryable:false}` | «объект удалён» |
| Удаление слоя, на котором кто-то рисует | `structural` исполняется первым по порядку; последующая операция получает `gone`/переехавший слой | предупреждение |
| Правка при `viewer` | `rejected{code:"forbidden", retryable:false}` | «только просмотр» |

Лимиты: ≤5000 затронутых сущностей в одной транзакции, ≤1 MiB на сообщение;
больше — `rejected{code:"too-large"}` с предложением разбить (массив/копирование
слоя).

### 4.5 Reconnect и догон

Клиент присылает `resync{lastVersion}`. Если версия в журнале — сервер шлёт `applied` (result.delta)
подряд (или батч `delta{more:true}`); иначе `snapshot` + `welcome`. После
ресинка клиент переотправляет непринятую очередь с теми же `opId` (дедуп их
отсечёт) и новым `baseVersion`.

### 4.6 Снапшоты и compaction (ADR-0005)

- Снапшот — DXF-байты `cadcraft_io::write_with` (ASCII, версия чертежа) +
  метаданные `{version, recordIds, handles, fileId, savedAt}`; передаётся
  чанками по 1 MiB (`snapshot.seq`/`more`), суммарный лимит — по размеру
  документа, а не по лимиту одного сообщения.
- Частота: 500 операций или 5 минут, и обязательно перед входом нового
  участника при журнале длиннее порога. Хранятся 2 снапшота.
- Восстановление = `read(snapshot)` + реплей журнала; handle'ы и `recordId`
  берутся из метаданных.
- Commit — отдельный формат и отдельная операция (§8); падение DWG-конвертера
  не ломает сессию.

## 5. Presence (ADR-0006)

Отдельный тип в том же WS, не журналируется, без подтверждений:
`{space, layout, mspace, cursor:[x,y] (WCS), viewport:{center,height}, selection:[handle], layer}`.
≤10 Гц на клиента, ≤2 KiB, коалесцировать в последнее состояние, при перегрузке
— drop-stale. TTL 30 с → «неактивен»; `leave`/разрыв WS чистят сразу. Viewer
шлёт presence, но не `op`. Содержимое чертежа и текст в presence не попадают.

## 6. Undo/redo на пользователя (ADR-0010)

- Сервер держит стек на `actor`: шаг = before-образы затронутых объектов +
  обратные табличные операции (`table.rename` обратно, `table.create` → delete).
- Undo — отдельное сообщение конверта `undo{opId}` (§4.2), а не команда в
  `op`: сырые команды на проводе запрещены allowlist'ом, а `undo` не должен
  зависеть от него. Undo применяется тем же путём, получает новый `version`,
  журналируется и рассылается как дельта.
- Redo — такое же сообщение `redo{opId}`: возвращает последнюю отменённую
  операцию, получает новый `version` и снова кладёт шаг в undo-стек. Любая
  новая операция участника (включая ещё один undo) очищает его redo-стек:
  ветка истории одна.
- Если затронутое изменено другим после шага — `rejected{code:"undo-conflict"}`,
  без частичного «умного» отката. Для redo — `redo-conflict`, если после undo
  кто-то (в том числе сам участник) изменил чертёж.
- Каскад (удаление слоя с объектами, удаление листа) хранится целиком и
  ограничен лимитом (≤5000 объектов / 8 MiB); иначе шаг не попадает в undo.
- Локальный стек `DocState.undo` для совместной сессии не используется: чужие
  дельты применяются **мимо** `push_undo` (нужен путь `apply_remote`), иначе
  чужая правка попадёт в локальную историю.
- Offline v1: только догон; автономные правки запрещены.

## 7. Роли и права (ADR-0008)

JWT первым сообщением; claims `{iss, aud:"office-sync", sub, fileId, app:"cadcraft",
role, sessionId, iat, exp}`. Проверка `aud/exp/fileId/sessionId` при подключении,
**роль — на каждую операцию**. `viewer`: `applied`, `snapshot`, `presence` — да,
`op`/`commit`/`undo`/`redo` — `rejected{forbidden}`. Клиент блокирует команды до
движка в единой точке (`CadApp::run` → `collab_command`), поэтому клавиатура,
меню и control-канал не обходят запрет; сервер остаётся авторитетом. Отдельный
`read-only` флаг в `Session` — открытый вопрос (§13): он нужен как второй барьер,
но требует признака «команда меняет документ» у `CommandSpec`. Lease: одна
комната на файл, продление `ping`, отзыв — закрытие WS по `sid`. Токен не в URL,
не в логах, не в снапшотах.

## 8. Commit и версии (ADR-0009)

1. `commit{expectedVersion}` (ответ — `commit-result`); сервер проверяет, что `version` совпадает с
   подтверждённой, и что файл не изменён извне (`expectedVersion`/etag исходника).
2. **До записи** — `loss_on_save` (`cmd/file.rs:835`): для DXF 2013+ —
   `sat_text_dropped`, для DWG — `not_saved_as`; список идёт в ответ (`notSaved`)
   и в аудит кабинета.
3. Сборка: DXF — `write_with` из авторитетного `Drawing`; DWG — через мост
   `acadrust` в **дочернем процессе** (`cadcraft_dwg::worker`) с таймаутом и
   размерным лимитом. Падение конвертера → `error{code:"dwg-failed"}`; DXF-версия
   при этом не теряется, сессия жива.
4. Ответ кабинету: `{bytes|uploadUrl, sha256, version, notSaved}`; кабинет
   создаёт новую версию, **предыдущую сохраняет**, пишет `notSaved` в аудит.
5. Внешнее изменение файла → `409`, предложение «сохранить копию»; сессия не
   перезаписывает.
6. Повторный commit с тем же `opId`/версией идемпотентен.
7. Приёмка: committed `.dxf` открывается в LibreCAD и QCAD без потерь геометрии
   и слоёв; `.dwg` — в доступном просмотрщике; `notSaved` совпадает с ожидаемым.

## 9. Сервер

- Новый крейт `cadcraft-collab-server` (бинарь) + адаптер `cadcraft-collab-proto`
  (общий конверт, per-app кодек). Статическая линковка `cadcraft-engine` +
  `cadcraft-io`; dylib-плагинов нет (house rules: `unsafe` forbid).
- Комната = `(fileId, app)`; воркер на документ, изоляция по памяти (200k
  сущностей — не общий OOM-домен).
- Хранение: 2 DXF-снапшота + журнал на volume/БД; lease — общий сервис
  (Redis/Postgres либо файл с lock, решение deployment).
- Лимиты: 8 участников (типично 2–5), 50 операций/с на комнату, 1 MiB сообщение,
  5000 сущностей/транзакция, 8 MiB дельта, 30 с presence TTL.
- Метрики: версия, длина журнала, applied/rejected по кодам, время применения,
  время diff, размер снапшота, commit (формат, мс, notSaved-счётчики), без
  содержимого чертежа.
- Healthcheck `/livez`, `/readyz`; логи без содержимого и токенов.
- Крейт живёт по тем же правилам, что остальные: `unsafe_code="forbid"`,
  `deny(unwrap_used, expect_used, panic, …)`, лицензии — из allowlist, CI не
  меняется в feature-PR.

**Diff «до/после».** Сервер держит `Arc<Drawing>` до операции; после — сравнивает
по чанкам (`EntityStore::same_as`/`chunk_slices`, `doc/src/store.rs:271,277`),
обходит только изменённые и формирует `entity.*`. Таблицы сравниваются по
`recordId`; переименование берётся из явной операции (`table.rename`), иначе
сервер не отличит его от delete+create. Геометрия `*D`/`*T` не сравнивается —
она производная.

## 10. Клиент

- **Feature flag:** native — `--collab-url`, `--collab-doc` и
  `CADCRAFT_COLLAB_TOKEN` (токен в окружении, не в списке процессов); web —
  `?collab=1` (ещё не подключён). По умолчанию режим выключен, одиночный не
  меняется.
- **Что уже сделано:** `Collab` в `ui-egui` держит соединение на своём потоке,
  `collab_tick` применяет `applied` через `Session::apply_remote` и отправляет
  presence ≤10 Гц; `CadApp::run` отправляет не-UI команды как `Op` (structural —
  для каскадов), viewer получает отказ; командная строка в совместной сессии
  принимает только однострочные команды с явными адресами
  (`cadcraft_collab::cmdline`, ADR-0018): `line`, `circle`, `arc`,
  `polyline`, `ellipse`, `rect`, `text`, `dimlinear`, `dimaligned`,
  `mleader`, `spline`, `block`, `insert`, `move`, `copy`, `rotate`,
  `mirror`, `scale`, `offset`, `trim`, `array`, `hatch`, `wipeout`,
  `imageattach`, `erase`.
  Синтаксис адресных форм:
  `line x,y x,y [x,y…]`, `circle x,y r`, `polyline x,y x,y [x,y…]`,
  `ellipse cx,cy rx[,ry] [angle]`, `rect x,y x,y`,
  `arc cx,cy r start end` (дуга по центру, радиусу и углам начала и конца в
  градусах, как у движковой `arc`; неположительный радиус, координата или
  радиус за лимитом чертежа и нечисловой угол отклоняются до операции),
  `text x,y height angle "content"` (содержимое в кавычках, `\"`/`\\` —
  экранирование; пустой текст и неположительная высота отклоняются),
  `dimlinear H1,H2 offset d` (линейный размер между характерными точками двух
  объектов; размерная линия параллельна измеряемой на подписанном расстоянии
  `d` влево от `H1 → H2`) или `dimlinear H1,H2 point x,y` (размерная линия в
  точке `x,y`); одинаковые handle, объект без характерной точки и нулевая длина
  отклоняются до операции,
  `dimaligned x1,y1 x2,y2 ax,ay` (выровненный размер между двумя явными
  точками `x1,y1` и `x2,y2`; размерная линия проходит через точку `ax,ay`;
  нечисловая или вне-лимитная координата и совпавшие измеряемые точки
  отклоняются до операции),
  `mleader H[,H…] x,y "text"` (выноска: стрелка в ближайшей характерной точке
  каждого названного объекта, посадка в точке `x,y`, текст в кавычках; пустой
  текст, объект без характерной точки и посадка на последнюю точку стрелки
  отклоняются до операции),
  `spline x,y x,y x,y [x,y…] [closed]` (3–64 точки подгонки, необязательное
  замыкание; точка вне лимита координат чертежа и меньше трёх точек
  отклоняются до операции),
  `block NAME base x,y H[,H…]` (новый блок из названных объектов с базовой
  точкой; объекты становятся одной ссылкой на него — умолчание BLOCK
  «Convert»; пустое, анонимное (`*…`) или уже занятое имя отклоняются до
  операции, определение уезжает репликам как `block.create`, ADR-0020),
  `insert NAME at x,y [scale s] [angle a]` (вставка блока по имени; масштаб
  положительный, угол в градусах; имя, которого нет в чертеже, и масштаб ≤ 0
  отклоняются до операции),
  `move H[,H…] delta dx,dy` (или `from x,y to x,y`), `copy H[,H…] dx,dy`,
  `rotate H[,H…] base x,y angle`, `mirror H[,H…] x1,y1 x2,y2`,
  `scale H[,H…] base x,y factor`,
  `offset H distance d side x,y` (копия на слое автора, ADR-0019),
  `trim H edge H[,H…] at x,y` (объект меняется на месте; если кромка не
  пересекает объект, строка отклоняется до операции),
  `array H[,H…] rows r cols c step dx,dy` (прямоугольный массив отдельных
  копий на слое автора, ADR-0019),
  `hatch H[,H…] pattern ANSI31 scale s angle a` (одна статическая штриховка по
  названным замкнутым объектам — кругу, замкнутой полилинии, полному эллипсу
  или замкнутому сплайну; `associative: false`, `separate: false`,
  `style: normal`; незамкнутый контур, неизвестный шаблон и нулевой масштаб
  отклоняются до операции),
  `wipeout x,y x,y x,y [x,y…]` или `wipeout H` (маскирующий полигон по точкам
  или по замкнутой полилинии, названной handle; маска едет точками границы,
  поэтому обе реплики рисуют одно и то же, а правка полилинии позже маску не
  двигает; незамкнутая полилиния, полилиния с дуговым сегментом, меньше трёх
  точек и контур без площади отклоняются до операции; `frames` — переменная
  чертежа, общей её не делает),
  `imageattach NAME data BASE64 [at x,y] [width w | scale s] [rotation deg] [name "Title"]`
  (растровая вставка: `NAME` — только метка, сохраняемая в чертеже, и она
  обязана оканчиваться на `png`/`jpg`/`jpeg`/`bmp`/`tif`/`tiff`; байты едут в
  `data` как base64 и декодируются сервером и автором, файл по клиентскому
  пути сервер не открывает (ADR-0021); `at` — нижний левый угол, по умолчанию
  `0,0`; ширина — в единицах чертежа (`width`) или `scale` при ширине 1;
  `rotation` в градусах; `name` переопределяет имя определения. Нечисловая
  координата, отсутствующая или битая base64, не-растровое расширение, данные
  сверх лимита операции 1 MiB, пустое имя и ненулевой поворот без ширины или
  масштаба отклоняются до операции; растр в change set не едет — получатель
  видит ту же рамку и метку, а пиксели остаются у автора),
  `erase H[,H…]`. Строка, которую парсер не
  разобрал целиком, отклоняется до создания операции, поэтому документ не
  меняется.
- **Presence на экране:** курсоры и имена других участников рисуются в текущем
  пространстве (цвет по имени, не в журнале); undo/redo перенаправлены на
  серверные сообщения `undo`/`redo`.
- **Интеграция:** `Session` остаётся движком; добавляется путь
  `apply_remote(changes)` (без `push_undo`, с обновлением чанков, R-tree по
  идентичности чанков и `revision`), и `execute_intent` с явным `context`.
- **Оптимистичный показ:** локальная команда исполняется как сейчас; при
  `rejected` — откат к версии из `applied`/`snapshot` (Arc-снапшот дешёв).
- **Viewer:** UI блокирует команды и показывает «только просмотр»; защита —
  серверная.
- **Presence:** рисуется поверх (курсоры/выделения в model space и на листе),
  список участников, индикатор синхронизации/ошибки.
- **Undo/redo:** кнопки шлют сообщения `undo`/`redo` на сервер; локальный стек
  не используется в совместной сессии. Redo доступен, пока участник не сделал
  новую операцию после отмены.

## 11. Тесты

Headless, 2–3 клиента, in-process сервер (без GUI); `cargo test` + отдельный
интеграционный набор `crates/collab/tests`:

1. Две операции над разными сущностями сходятся; состояния равны (сравнение
   `Drawing`).
2. Одна сущность: вторая правка даёт `conflict:true` и одинаковый результат.
3. Слои: создать/переименовать/удалить при активных участниках; сущности
   переезжают, `recordId` сохраняется; `laydel` — одна транзакция.
4. Блоки: переопределение и переименование при живых `INSERT`; атрибуты.
5. Размеры/штриховки: ассоциативность после чужой правки геометрии; границы.
6. Листы/вьюпорты: создание/удаление листа, `viewport.clip` на удалённый объект.
7. Порядок отрисовки: параллельные `draworder` сходятся по якорю.
8. Reconnect: догон по `version`, ресинк снапшотом, дедуп `opId` после рестарта.
9. Viewer: `op` → `forbidden`; presence проходит.
10. Undo/redo: два клиента отменяют каждый своё; отмена не трогает чужое;
    `undo-conflict`; redo возвращает отменённое; `redo-conflict` после чужой
    правки; новая операция сбрасывает redo-ветку; undo каскада слоя.
11. Большой чертёж: 10k+ сущностей, время diff и применения в бюджете; дельта
    не превышает лимит.
12. Commit: `.dxf`/`.dwg`, `notSaved`, 409 при внешнем изменении, идемпотентность;
    открытие в LibreCAD/QCAD (ручной gate, отмечен в PR).
13. Round-trip: commit → reopen → геометрия, слои, блоки, `foreign` совпадают
    (по `io::roundtrip::compare`).
14. Растр: `imageattach` с `data` доходит до двух реплик одной рамкой и меткой;
    операция без `data` отклоняется сервером до мутации, а битая base64,
    не-растровое расширение и данные сверх лимита — парсером; undo/redo —
    один шаг, пиксели в change set не едут (ADR-0021).

## 12. Безопасность

JWT (ADR-0008), WSS, `Origin` для web, лимиты сообщений и операций, размер
документа, число участников. Логи: `sub`, `opId`, `version`, коды ошибок; без
содержимого, без токенов, без путей пользователя. Снапшоты не отдаются в
кабинет; commit — по контракту кабинета. Антивирус/аудит — на стороне кабинета.
`imageattach` в совместной сессии принимает растр только в `data` (≤1 MiB на
операцию): `path` — метка, сервер не открывает файл по клиентскому пути и не
отвечает, существует ли он (ADR-0021). Серверное хранилище вложений (`--assets`)
с проверкой после нормализации и `realpath` — следующий срез.

## 13. Открытые вопросы

1. Allowlist v1: какие команды CADCraft разрешены в совместном режиме
   (предлагаю: draw/modify/props/layer/block/layout/draworder/erase/dimension
   базовые; `open`, `saveas`, `new`, `recover`, `purge`, LISP, `audit` — запрещены).
2. Формат `primitive`-операций: общий словарь на пять приложений или per-app.
3. Порог «слишком большой операции» и поведение UI (разбить автоматически или
   предложить пользователю).
4. Место хранения журнала/снапшотов (volume, БД) и TTL после commit.
5. Нужен ли `read-only` флаг в `Session` (сейчас клиент блокирует до движка, а
   сервер — авторитет) и как пометить «команда меняет документ» в `CommandSpec`.
6. Различать окна одного пользователя (`clientId` в presence и ключ доски) и
   отдавать роли в `welcome.participants[]` — иначе два окна одного `sub`
   перетирают курсор, а панель участников знает роль только про себя.
