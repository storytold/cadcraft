## 1. Контекст

CADCraft сейчас — одиночный редактор: один пользователь, один чертёж, одна
сессия. Правка идёт командами (`CommandSpec::run: fn(&mut Session, &Value)`,
`crates/engine/src/cmd.rs:69`), после каждой undoable-команды движок делает
глобальные пост-проходы — параметрический решатель (`cmd/constraints.rs:1136`),
ассоциативные размеры (`assoc.rs:402`), группы — и может изменить сущности,
которых команда не касалась. Undo — снапшот всего `Arc<Drawing>` на документ
(`doc_state.rs:5`), без автора и инверсий. Сети в проекте нет: ни одной прямой
зависимости с `tokio`/WebSocket; web-сборка общается с кабинетом через
`craft-web-host` (`apps/cadcraft-web/src/host.rs`).

Главное ограничение проекта: **DXF пишет обратно то, что не моделируется**
(`Unknown` + `foreign`, raw-проход `dxf_raw::finish`), а **DWG-мост теряет часть
этих данных**; `loss_on_save` (`cmd/file.rs:873`) уже считает потери до записи.
Поэтому commit обязан нести `notSaved`, а кабинет — хранить предыдущую версию.

## 2. Цели и не-цели

**Цели.** Совместное редактирование одного чертежа 2–5 участниками в реальном
времени: сущности, слои, блоки, размеры, штриховки, листы и вьюпорты; presence;
роли; per-user undo; commit в `.dxf`/`.dwg` с новой версией в кабинете.

**Не-цели.** Оффлайн-редактирование, CRDT/OT, совместная работа с разными
чертежами, полная совместимость с AutoCAD, изменение поведения одиночного
режима, 3D.

## 3. Модель данных для синхронизации

**Документ на сервере.** Авторитетная копия — `cadcraft_engine::Session` с одним
`Drawing` и фиксированным контекстом (активное пространство приходит в операции,
а не берётся из окна). Состояние сессии = **снапшот + хвост журнала**
(ADR-0005). Снапшот — DXF-байты `write_with` **плюс sidecar непромоделированного
и неперезаписываемого**: писатель возвращает raw-проходом `Unknown`/`foreign` и
xdata, но не всё, что было в исходном файле. В частности, DXF 2013+ с
SAT-text `3DSOLID`/`REGION`/`BODY` без ACIS data-store записей теряет эти тела
(`crates/doc/src/foreign.rs`): raw-проход их не восстанавливает, и рестарт из
одного DXF молча терял бы геометрию. Поэтому sidecar хранит такие записи
(исходные группы/байты ACIS) и их `sha256`, а `read` накладывает их после DXF;
без sidecar снапшот невалиден. DWG в снапшот не идёт (мост — отдельный процесс,
ADR-0005).

**Единица операции (ADR-0001).** Транзакция одного пользовательского действия:

```
op = { opId, sessionId, actor, baseVersion, kind, payload, context }
kind ∈ "command" | "primitive" | "structural"
context = { space: "model" | "paper", layout?: string, mspace?: handle,
            selection?: [handle], clay?: string }
```

Типы на проводе: `handle` — hex-строка `u64` в верхнем регистре (`"2A1"`, не
число); `recordId` — UUID строкой; `clay` — имя текущего слоя (необязательное,
для команд, читающих `CLAYER`), а не `recordId`.

**Автор и id операции — не поля клиента.** `actor` и `sessionId` в конверте
информативные: сервер **игнорирует** присланные значения, берёт автора из
проверенного JWT (`sub`), а сессию — из соединения (`welcome.sessionId`);
`applied.actorId` — всегда результат проверки токена, а не эхо клиента. Иначе
клиент подписал бы правку чужим именем (замечание pdfcraft
`20261108T103023Z-pdfcraft-2193`, ADR-0008). `opId` формирует клиент как
`clientId:seq`: `clientId` приходит в `welcome` (§4.2), `seq` — монотонный
счётчик, который не сбрасывается при reconnect; сервер `opId` не
перегенерирует, а использует как ключ дедупа (§4.3).

**`clientId` живёт дольше соединения.** Сервер выдаёт его при первом успешном
`hello` и привязывает к проверенному `sub`; клиент хранит его в локальном
состоянии сессии вместе с последним `seq`. При reconnect клиент присылает
`hello.clientId?`; сервер принимает его, только если тот принадлежит тому же
`sub` и ещё не выдан другому соединению, иначе выдаёт новый. Пока живёт lease
участника или окно дедупа, `clientId` действителен: `seq` продолжается, а
повтор с тем же `opId` попадает в окно дедупа и получает прежний `applied`.
Новый `clientId` начинает `seq` с нуля; сервер отвергает `opId`, чей `clientId`
выдан другому `sub` или другому соединению того же `sub` (окна одного
пользователя не подменяют друг друга).

- `kind:"command"` — id команды + JSON-параметры (форма `engine.execute`), но
  адреса явные: `space`/`layout`, выбранные handle'ы, а не состояние окна.
- `kind:"primitive"` — нормализованная операция там, где команды нет или где
  нужна одна атомарная единица: `table.rename`, `table.delete`, `layout.create`,
  `order.move`, `entity.group.*`.
- `kind:"structural"` — операция, чей результат зависит от других объектов
  (каскад): удаление/переименование слоя, переопределение блока, удаление листа,
  удаление сущности со ссылками.

**Ответ (ADR-0001, 0003).** Авторитетный результат: `version`, подтверждённая
операция и **дельта модели**:

```
changes = [
  {t:"entity.create", handle, space, order:{after|before|bottom|top}, entity},
  {t:"entity.replace", handle, entity},
  {t:"entity.delete", handle},
  {t:"entity.order", handle, order},
  {t:"table.create|table.update|table.rename|table.delete", recordId, kind, …},
  {t:"layout.create|layout.rename|layout.delete", recordId, …},
  {t:"drawing.header", key, value}
]
```

Производное не едет: блоки `*D`/`*T` генерируются при записи
(`io/src/dxf_write/blocks.rs:19`), решатель и ассоциативность — на сервере.

**Идентификаторы (ADR-0002).**
- Сущность — `Handle(u64)`, выдаёт сервер из `handseed`; он стабилен и переживает
  save/load, поэтому в дельте едет handle.
- Запись таблицы имён (`layer`, `linetype`, `text/dim/mleader/table/mline style`,
  `layout`, `group`, `layer state`) — `recordId` (UUID), выдаётся на сессию;
  имя — изменяемое значение, не ключ. Сервер ведёт карту `recordId ↔ имя`.
  Без этого переименование слоя выглядело бы как удаление + создание.
- Порядок отрисовки — позиция в `EntityStore`, поэтому в дельте он адресуется
  якорем (`after`/`before`/`top`/`bottom` по handle), а не индексом.
- Надгробия: удалённый `recordId`/`handle` не переиспользуется в сессии;
  операция по удалённому адресу отклоняется (`retryable:false`).
- **Позиционные адреса и `epoch` (ADR-0012).** В CAD адрес — `Handle`/`recordId`,
  а не индекс: structural-правка (удаление слоя, листа, перестановка порядка)
  адреса не сдвигает, поэтому `epoch` не нужен — осознанное отличие от PDF,
  Grid, Word и Deck, где `epoch` обязателен. От повторов защищает `version`/
  `baseVersion` и дедуп `opId` (§4.3).

## 4. Протокол

### 4.1 Транспорт

WSS, один канал на комнату `(fileId, app="cadcraft")`. Фрейм — JSON (UTF-8),
лимит 1 MiB на сообщение; дельта больше 1 MiB дробится на несколько `applied` с
флагом `more:true` (см. §4.3, ADR-0013). Presence — ≤2 KiB. Бинарные фреймы не
нужны: геометрия — f64 в JSON (`serde_json` с `float_roundtrip` у обеих сторон).
Native-клиент — Rust WebSocket; WASM — `web-sys::WebSocket`, всё в кадре egui,
без блокирующих вызовов.

### 4.2 Сообщения

Имена и поля — по общему конверту `.craft/protocol/ARCHITECTURE.md` §2: `hello`,
`welcome`, `op`, `undo`, `redo`, `applied`, `rejected`, `presence`, `resync`,
`snapshot`, `commit`, `commit-result`, `error`, `ping`/`pong`. Приложение
уточняет только тело `target`/`payload` и `result`.

| Тип | Направление | Поля | Семантика |
|---|---|---|---|
| `hello` | C→S | `{app:"cadcraft", doc, jwt, protoVersion:1, client{name,ver}, clientId?, lastVersion?}` | JWT первым сообщением, не в URL (ADR-0008); `clientId?` — сохранённый id окна для продолжения `seq` (§3) |
| `welcome` | S→C | `{sessionId, clientId, actorId, role, lease, version, participants[], capabilities, protoVersion, snapshot?}` | `clientId` — id этого окна, живёт дольше соединения (§3); `snapshot` — ссылка на базу, если `lastVersion` вытеснен |
| `op` | C→S | `{opId, baseVersion, kind, target, payload, preview?}` | намерение; `target` несёт `space`/`layout`/`selection` (§3) |
| `undo` | C→S | `{opId, targetOpId?}` | отменить последнюю операцию участника (или названную `targetOpId`); ответ — `applied` или `rejected{code:"undo-conflict"}`; это не `op` с командой `undo`, а отдельное сообщение конверта |
| `redo` | C→S | `{opId, targetOpId?}` | вернуть последнюю отменённую операцию; ответ — `applied` или `rejected{code:"redo-conflict"}` |
| `applied` | S→C | `{opId, version, actorId, result:{command?, delta?, conflict?}, more?, seq?, total?}` | авторитетный результат для **всех**, включая автора: `delta` едет всегда, `command` — подтверждённое намерение; длинная дельта дробится с `more:true` и нумеруется `seq`/`total`, `sha256` всей дельты — в первом чанке (§4.3) |
| `rejected` | S→C | `{opId, code, message, retryable, hint?}` | отказ; коды — закрытый список §4.2a (`stale`, `gone`, `forbidden`, `invalid`, `too-large`, `rate-limited`, `undo-conflict`, `redo-conflict`, `auth`, `lease`, `external-change`, `unsupported`) |
| `presence` | C↔S | `{clientId, space, layout, cursor:[x,y], viewport, selection[], layer, mspace}` | не журналируется, без подтверждений; `clientId` различает окна одного `sub` |
| `resync` | C→S | `{lastVersion}` | догон или база + хвост (§4.5) |
| `snapshot` | S→C | `{version, generation, seq, total, more, bytesBase64, sha256, meta}` | чанки по 1 MiB (`seq` с 0, `more` у всех кроме последнего, `sha256` — всего файла и повторяется в каждом чанке); непринятая очередь **сохраняется** (§4.5) |
| `commit` | C→S | `{opId, expectedVersion}` | запрос сборки файла (ADR-0009); `opId` — ключ идемпотентности повтора |
| `commit-result` | S→C | `{opId, version, sha256, size, notSaved, bytes? \| chunk? \| uploadUrl?}` | результат commit; путь крупного файла — §8 |
| `error` | S→C | `{code, message, retryable}` | общие ошибки (auth, lease, лимиты); `rejected` — про операцию, `error` — про соединение |
| `ping`/`pong` | C↔S | `{ts}` | lease продлевается `ping`; `ts` — для измерения RTT, не для порядка |

Отклонение от общего конверта одно и записано явно: `snapshot` чанкуется по
1 MiB, потому что DXF на 100 MB в base64 — это ~133 MB одним сообщением
(замечание gridcraft к ревью `rfc/cadcraft`).

`capabilities` в `welcome` фиксирует `{kinds:["command","primitive","structural"],
limits:{…}, protoVersion}`; неизвестные поля сообщений игнорируются
(forward-compatibility), неизвестный `kind`/`target` — `unsupported` до мутации.
`protoVersion` в `hello` и `welcome` обязателен: несовпадение — `unsupported`
с перечислением поддерживаемых версий.

### 4.2a Коды отказа и сверка авторского результата

Коды `rejected` закрыты; новый код — изменение RFC, а не расширение на месте.
Код `conflict` отказом не является: конфликт едет флагом в `applied` (§4.4).
`rejected.opId` — идентификатор запроса; `hint` несёт машиночитаемые детали
(`version`, `retryAfterMs`), `message` — текст для пользователя. `error` —
про соединение, `rejected` — про конкретную операцию.

| code | retryable | что делает клиент |
|---|---|---|
| `stale` | да | догоняет до head по `applied`/`resync` и **переотправляет** ту же операцию с тем же `opId` и новым `baseVersion` (§4.4) |
| `gone` | нет | убирает адрес из превью и выделения, показывает «объект удалён» |
| `forbidden` | нет | показывает «только просмотр»; операция не повторяется |
| `invalid` | нет | правит параметры (схема/глубина JSON/экранирование, §12) |
| `too-large` | нет | дробит операцию (массив или копирование слоя) |
| `rate-limited` | да | ждёт `hint.retryAfterMs`, затем повторяет с тем же `opId` |
| `undo-conflict` / `redo-conflict` | нет | перечитывает стек: шаг уже изменён другим участником |
| `auth` / `lease` | нет / да | `auth` — сессия окончена; `lease` — новый `hello` и `resync` |
| `external-change` | нет | предлагает «сохранить копию»; файл изменён вне сессии (§8) |
| `unsupported` | нет | клиент и сервер не сошлись в `protoVersion`/`capabilities` |

**Автор получает ту же дельту.** Оптимистичный локальный результат — догадка:
сервер применяет операцию к head, выдаёт handle'ы из своего `handseed` и делает
пост-проходы (решатель, ассоциативность, группы), поэтому локальная геометрия
может отличаться. Поэтому `applied` автору несёт `delta` наравне с остальными,
а `command` — только подтверждённое намерение. Клиент применяет `delta` к
состоянию `baseVersion` и **заменяет** ею свою превью-транзакцию: созданные
объекты сопоставляются по порядку создания в дельте и в локальной транзакции,
при любом расхождении побеждает дельта (в том числе handle'ы, порядок отрисовки
и результат пост-проходов). Сохранять локальный результат рядом с дельтой
нельзя — это дало бы две версии одного объекта.

### 4.3 Порядок и версии (ADR-0003)

- Один монотонный `version` на чертёж, без пропусков; увеличивается каждой
  принятой операцией (`presence` не увеличивает).
- `opId = clientId:seq` (формирует клиент, §3); окно идемпотентности ≥24 ч
  или ≥10 000 операций. Повтор возвращает сохранённый `applied`, операция
  **не исполняется второй раз** (иначе повторно выделятся handle и сработают
  пост-проходы).
- **Окно дедупа переживает compaction и рестарт.** Результаты `opId` →
  `{version, applied}` (или хэш ответа) лежат не только в журнале: они входят в
  метаданные снапшота (§4.6) и восстанавливаются **до** приёма новых операций.
  Обрезка журнала после снапшота их не стирает; без этого повтор в обещанном
  окне исполнился бы второй раз после рестарта.
- `baseVersion` — контекст. `kind:"structural"` требует `baseVersion == head`
  и исполняется в эксклюзивной секции; остальные применяются к head.
- Клиент применяет `applied` только при `version = local+1`; иначе просит
  `snapshot` и сохраняет непринятую очередь (§4.5).
- Чанки одной дельты идут подряд и не перемежаются чужими `applied`: версия
  фиксируется на первом чанке, клиент применяет документ только после
  `more:false`, а следующие сообщения ждут. Иначе клиент получил бы половину
  версии N, сверху версию N+1 и другое состояние. Это правила 1–3 ADR-0013;
  остальные: лимит 8 MiB на дельту при 1 MiB на сообщение (превышение —
  `rejected{code:"invalid"}` до рассылки), а `resync{lastVersion}` после обрыва
  в середине чанков переигрывается с версии до первого чанка, а не с середины
  (правила 5–6).

### 4.4 Конфликты (ADR-0004)

| Ситуация | Политика | Что видит пользователь |
|---|---|---|
| Двое правят разные сущности | обе применяются по порядку сервера | обе правки |
| Двое правят одну сущность | вторая применяется к head, ответ несёт `conflict:true`; правка атомарна (вся сущность) | «объект изменён другим участником», новая версия объекта |
| Двое правят свойства одной сущности (слой, цвет) | то же: сервер применяет к head, `conflict:true` | как выше |
| `structural` при устаревшем `baseVersion` | `rejected{code:"stale", retryable:true, hint:{version:head}}`; сервер **не** ставит операцию в очередь и не перебазирует её; клиент догоняет head по `applied`/`resync` и **переотправляет** ту же операцию с тем же `opId` и новым `baseVersion` — ровно один раз, дальше только по новой правке пользователя | «структурная операция ждёт синхронизации» |
| Операция по удалённой сущности/слою | `rejected{code:"gone", retryable:false}` | «объект удалён» |
| Удаление слоя, на котором кто-то рисует | `structural` исполняется первым по порядку; последующая операция получает `gone`/переехавший слой | предупреждение |
| Правка при `viewer` | `rejected{code:"forbidden", retryable:false}` | «только просмотр» |

Лимиты — одна таблица §9: ≤5000 затронутых сущностей в одной транзакции
(и ≤50 000 просмотренных), ≤1 MiB на сообщение, ≤8 MiB на дельту,
≤50 операций/с; больше — `too-large`/`rate-limited` с предложением разбить
(массив/копирование слоя) или повторить позже. Лимит просмотренных сущностей
важен для `laydel` и переименования слоя: они проходят весь чертёж, а не только
изменённые объекты.

### 4.5 Reconnect и догон

Клиент присылает `resync{lastVersion}`. Если версия в журнале — сервер шлёт
`applied` с `result.delta` по одному на версию, батчем не больше 100 версий
(`more:true` на границе батча, клиент просит `resync` снова); отдельного
сообщения `delta` нет — догон идёт теми же `applied`. Если версия вытеснена или
хвост длиннее 1000 версий — `snapshot` (плюс `welcome`, если сменилась сессия).

`welcome.snapshot` — не байты, а ссылка `{mode:"base"|"base+tail", version,
generation, cursor}`: клиент знает, что база придёт чанками, и ждёт `snapshot`.
Клиент применяет снапшот как базу версии `version` и **сохраняет непринятую
очередь**: операции остаются в ней до `applied` с их `opId` или до
`rejected` с `retryable:false`. После снапшота клиент переотправляет очередь с
теми же `opId` и новым `baseVersion`; сервер отвечает из окна дедупа, если
операция уже принята, и `gone`/`stale` — если её адреса ушли. Обрыв в середине
чанков: недособранный снапшот отбрасывается, `resync` начинается с первого
чанка, а не с середины (правило 6 ADR-0013). Отброшенных молча операций нет:
очередь либо подтверждена, либо получила отказ с кодом.

### 4.6 Снапшоты и compaction (ADR-0005, ADR-0024)

- Снапшот — **поколение из трёх частей**: (1) DXF-байты `write_with` (ASCII,
  версия чертежа); (2) sidecar непромоделированного — SAT-text
  `3DSOLID`/`REGION`/`BODY` без ACIS data-store записей и прочее, что писатель
  не выводит обратно (§3), с собственным `sha256`; (3) метаданные
  `{format:1, version, generation, recordIds, handles, fileId, savedAt, dedup,
  sha256:{dxf, sidecar}}`.
- Части принадлежат одному `generation`; метаданные фиксируются последними
  (temp → `fsync` → rename), пара валидна только при совпадении `generation` и
  `sha256` — иначе читается предыдущее поколение (ADR-0024 п.3–4). Снапшот без
  sidecar невалиден: молча потерянная геометрия хуже отказа комнаты.
- Передача — чанками по 1 MiB (`snapshot.seq`/`total`/`more`, `sha256` всего
  файла в каждом чанке), суммарный лимит — по размеру документа, а не по лимиту
  сообщения.
- **Одна политика частоты и retention:** снапшот пишется при 500 операциях, или
  раз в 5 минут (`--snapshot-secs 300`), или при журнале ≥64 MiB — что раньше;
  хранятся 2 поколения (`current`, `prev`). Отдельного «30-секундного»
  снапшота с другим смыслом нет.
- **Окно дедупа — в снапшоте, не только в журнале.** `dedup` хранит
  `opId → {version, delta}` в пределах 32 MiB и ≥24 ч/≥10 000 операций, что
  раньше; при переполнении вытесняются самые старые записи, но повтор **никогда
  не исполняется второй раз**: вытесненный повтор получает
  `rejected{code:"stale", hint:{version}}` и догон, а не повторное исполнение.
- Обрезка журнала — только после фиксации и read-back нового поколения; потеря
  хвоста после версии снапшота допустима и называется клиенту (ADR-0024 п.6).
- Восстановление = снапшот (DXF + sidecar) + реплей журнала; handle'ы и
  `recordId` берутся из метаданных, окно дедупа — из `dedup`.
- Требование к реализации: запись снапшота не держит операционный путь —
  `Arc<Drawing>` клонируется, DXF пишется вне секции применения, а версия
  снапшота фиксируется до записи. Время записи на 200k сущностей — в замерах
  (`study.md` §8), интервал выводится из него.
- Commit — отдельный формат и отдельная операция (§8); падение DWG-конвертера
  не ломает сессию.

## 5. Presence (ADR-0006)

Отдельный тип в том же WS, не журналируется, без подтверждений:
`{clientId, space, layout, mspace, cursor:[x,y] (WCS), viewport:{center,height},
selection:[handle], layer}`. `clientId` различает окна одного `sub`: без него два
окна перетирали бы курсор друг друга. ≤10 Гц на клиента, ≤2 KiB, коалесцировать
в последнее состояние, при перегрузке — drop-stale. TTL 30 с → «неактивен»;
`leave`/разрыв WS чистят сразу. Viewer шлёт presence, но не `op`. Содержимое
чертежа и текст в presence не попадают.

## 6. Undo/redo на пользователя (ADR-0010)

- Сервер держит стек на `actor`: шаг = before-образы затронутых объектов +
  обратные табличные операции (`table.rename` обратно, `table.create` → delete).
- Undo — отдельное сообщение конверта `undo{opId}` (§4.2), а не команда в
  `op`: сырые команды на проводе запрещены allowlist'ом, а `undo` не должен
  зависеть от него. Undo применяется тем же путём, получает новый `version`,
  журналируется и рассылается как дельта.
- Redo — такое же сообщение `redo{opId}`: возвращает последнюю отменённую
  операцию, получает новый `version` и снова кладёт шаг в undo-стек. Любая
  новая операция участника (включая ещё один undo) очищает его redo-стек:
  ветка истории одна.
- Если затронутое изменено другим после шага — `rejected{code:"undo-conflict"}`,
  без частичного «умного» отката. Для redo — `redo-conflict`, если после undo
  кто-то (в том числе сам участник) изменил чертёж.
- Каскад (удаление слоя с объектами, удаление листа) хранится целиком и
  ограничен лимитом (≤5000 объектов / 8 MiB); иначе шаг не попадает в undo.
- Локальный стек `DocState.undo` для совместной сессии не используется: чужие
  дельты применяются **мимо** `push_undo` (нужен путь `apply_remote`), иначе
  чужая правка попадёт в локальную историю.
- Offline v1: только догон; автономные правки запрещены.

## 7. Роли и права (ADR-0008)

JWT первым сообщением; claims `{iss, aud:"office-sync", sub, fileId, app:"cadcraft",
role, sessionId, iat, exp}`. Все claims **обязательны**: `iss`/`aud` сверяются с
`--issuer`/`--audience`, `fileId`/`sessionId` — с `--file`/`--session`, `app` —
`"cadcraft"`; алгоритм закреплён (HS256 с секретом кабинета либо проверочный
ключ асимметричной схемы), `alg:none` и чужие `alg` отвергаются. Проверка — при
подключении, затем **`exp` и `role` перепроверяются на каждом `op`/`undo`/`redo`/
`commit` и на `ping`**; истёкший или отозванный токен получает `rejected{auth}`
и соединение закрывается, а не продлевает lease. `viewer`: `applied`,
`snapshot`, `presence` — да, `op`/`commit`/`undo`/`redo` —
`rejected{forbidden}`. Клиент блокирует команды до движка в единой точке
(`CadApp::run` → `collab_command`), поэтому клавиатура, меню и control-канал не
обходят запрет; сервер остаётся авторитетом. Политика команд —
**default-deny**: исполняются только адресуемые команды v1 (ADR-0018) и
`primitive`-операции из словаря; неизвестный `kind`/`target` — `unsupported`
до мутации. Deny-list в `deployment.md` перечисляет имена, которые нельзя
добавить в allowlist. Отдельный `read-only` флаг в `Session` — открытый вопрос
(§13): он нужен как второй барьер, но требует признака «команда меняет
документ» у `CommandSpec`. Lease: одна комната на файл, продление `ping`,
максимальный TTL — 10 минут, отзыв — отказ в операциях и закрытие WS по `sid`.
Токен не в URL, не в логах, не в снапшотах.

## 8. Commit и версии (ADR-0009)

1. `commit{opId, expectedVersion}`; `opId` — ключ идемпотентности: повтор с тем
   же `opId` возвращает сохранённый `commit-result`, а не собирает файл заново.
   Сервер проверяет, что `version` совпадает с подтверждённой (`stale` иначе).
2. **Внешнее изменение проверяет кабинет, а не сервер.** Владелец файла — кабинет:
   сервер передаёт `expectedVersion` и `sourceSha256` (хэш исходника, с которого
   комната стартовала/последний раз коммитила), кабинет атомарно сверяет их под
   своей блокировкой и отвечает `409`; сервер ретранслирует это как
   `rejected{code:"external-change", retryable:false}`. Клиент предлагает
   «сохранить копию»; сессия не перезаписывает файл. Одна сторона отвечает за
   проверку — кабинет; сервер отвечает только за `version`.
3. **До записи** — `loss_on_save` (`cmd/file.rs:873`): для DXF 2013+ —
   `sat_text_dropped` (тела `3DSOLID`/`REGION`/`BODY` без ACIS data-store
   записей), для DWG — `not_saved_as`; в снапшот такие тела идут sidecar'ом
   (§4.6), в commit — либо в sidecar рядом с файлом, либо в счётчик потерь.
   Схема ответа: `notSaved = {format, dropped:[{what, count}], sidecar:bool}`;
   список идёт в ответ, в UI и в аудит кабинета.
4. Сборка: DXF — `write_with` из авторитетного `Drawing`; DWG — через мост
   `acadrust` в **дочернем процессе** (`cadcraft_dwg::worker`) с таймаутом и
   размерным лимитом. Падение конвертера → `error{code:"dwg-failed"}`; DXF-версия
   при этом не теряется, сессия жива.
5. **Крупный файл не едет одним сообщением.** Лимит 1 MiB на сообщение
   действует и на `commit-result`: если base64 файла больше **512 KiB**
   (≈384 KiB сырых), `commit-result` несёт не `bytes`, а ссылку
   `{uploadUrl:"/commit/<opId>", size, sha256, expiresAt}`; кабинет забирает
   файл HTTP `GET` с `Range` и тем же JWT, сверяет `sha256` и только потом
   создаёт версию, а сервер удаляет объект после подтверждения или по TTL.
   Ниже порога — `bytes` в ответе, как раньше. `snapshot` уже чанкуется (§4.6),
   отдельного «большого» протокола нет.
6. Ответ кабинету: `{bytes|uploadUrl, sha256, size, version, notSaved}`; кабинет
   создаёт новую версию, **предыдущую сохраняет**, пишет `notSaved` в аудит.
   Коммит считается принятым только после сверки `sha256` на стороне кабинета.
7. Приёмка: committed `.dxf` открывается в LibreCAD и QCAD без потерь геометрии
   и слоёв; `.dwg` — в доступном просмотрщике; `notSaved` совпадает с ожидаемым;
   файл >512 KiB проходит путь `uploadUrl` и совпадает по `sha256`.

## 9. Сервер

- Новый крейт `cadcraft-collab-server` (бинарь) + адаптер `cadcraft-collab-proto`
  (общий конверт, per-app кодек). Статическая линковка `cadcraft-engine` +
  `cadcraft-io`; dylib-плагинов нет (house rules: `unsafe` forbid).
- Комната = `(fileId, app)`; воркер на документ, изоляция по памяти (200k
  сущностей — не общий OOM-домен).
- Хранение: 2 поколения снапшота (DXF + sidecar + метаданные, §4.6) + журнал на
  volume/БД; lease — общий сервис (Redis/Postgres либо файл с lock, решение
  deployment). Файлы состояния — `0600` в приватном каталоге (deployment).
- **Лимиты — одна таблица, на неё ссылаются RFC и deployment:**

  | лимит | значение | превышение |
  |---|---|---|
  | участников в комнате | 8 (типично 2–5) | `error{code:"lease"}` |
  | операций | 50/с на комнату и на `sub` (burst 100) | `rejected{code:"rate-limited", hint.retryAfterMs}` |
  | сообщение | 1 MiB | `rejected{invalid}` |
  | дельта | 8 MiB | `rejected{invalid}` до рассылки |
  | сущностей в транзакции | 5000 затронутых и 50 000 просмотренных (`laydel`/`repoint` — O(n)) | `too-large`; просмотр сверх бюджета — отказ, не фон |
  | presence | 10 Гц, 2 KiB, TTL 30 с | drop-stale |
  | очередь отправки участнику | 2 MiB | разрыв соединения (slow consumer) |
  | снапшот | 512 MiB | комната не стартует/отказывает в join |
  | журнал | 64 MiB | внеочередной снапшот |
  | `hello` без токена | 5 с, слот участника не занимает | `error{auth}`, закрытие |
  | соединений с одного IP | 32 | `error{lease}` |

- **Очередей, которые перебазируют операции, нет.** Structural не копится на
  сервере (§4.4); ограничены только очередь отправки (2 MiB) и окно дедупа
  (32 MiB, §4.6). Переполнение — отказ с кодом, а не рост памяти.
- Метрики: версия, длина журнала, applied/rejected по кодам, время применения,
  время diff, размер снапшота, commit (формат, мс, notSaved-счётчики), без
  содержимого чертежа.
- Healthcheck `/healthz`, `/readyz`; `/metrics` — только на loopback или с тем
  же JWT (`--metrics-token`); логи без содержимого и токенов.
- Крейт живёт по тем же правилам, что остальные: `unsafe_code="forbid"`,
  `deny(unwrap_used, expect_used, panic, …)`, лицензии — из allowlist, CI не
  меняется в feature-PR.

**Diff «до/после».** Сервер держит `Arc<Drawing>` до операции; после — сравнивает
по чанкам (`EntityStore::same_as`/`chunk_slices`, `doc/src/store.rs:271,277`),
обходит только изменённые и формирует `entity.*`. Таблицы сравниваются по
`recordId`; переименование берётся из явной операции (`table.rename`), иначе
сервер не отличит его от delete+create. Геометрия `*D`/`*T` не сравнивается —
она производная. `laydel` и `repoint` при переименовании — полный проход по
чертежу: они считают **просмотренные** сущности, а не только изменённые, и
упираются в лимит таблицы выше; замер на 200k — `study.md` §6/§8.

## 10. Клиент

- **Feature flag:** native — `--collab-url`, `--collab-doc` и
  `CADCRAFT_COLLAB_TOKEN` (токен в окружении, не в списке процессов); web —
  `?collab=1` (ещё не подключён). По умолчанию режим выключен, одиночный не
  меняется.
- **Что уже сделано:** `Collab` в `ui-egui` держит соединение на своём потоке,
  `collab_tick` применяет `applied` через `Session::apply_remote` и отправляет
  presence ≤10 Гц; `CadApp::run` отправляет не-UI команды как `Op` (structural —
  для каскадов), viewer получает отказ; интерактивная командная строка в
  совместной сессии пока запрещена (нужен явный контекст, а не промпты).
- **Presence на экране:** курсоры и имена других участников рисуются в текущем
  пространстве (цвет по имени, не в журнале); undo/redo перенаправлены на
  серверные сообщения `undo`/`redo`.
- **Интеграция:** `Session` остаётся движком; добавляется путь
  `apply_remote(changes)` (без `push_undo`, с обновлением чанков, R-tree по
  идентичности чанков и `revision`), и `execute_intent` с явным `context`.
- **Оптимистичный показ:** локальная команда исполняется как сейчас; при
  `applied` автор применяет авторитетную дельту и заменяет ею превью (§4.2a);
  при `rejected` — откат к версии из `lastVersion`/`snapshot` (Arc-снапшот дешёв).
- **Рендер не пересобирается на каждую дельту:** `render::build` вызывается не
  чаще одного раза на кадр или на пачку версий; пачка из N `applied` даёт один
  проход. Время кадра под очередью дельт — замер в `study.md` §8.
- **Снапшот применяется не одним кадром:** чанки копятся в буфер (или сразу в
  временный файл), проверяются `sha256`, и `read` выполняется частями с
  уступкой кадру; UI показывает `Resyncing` до последнего чанка.
- **Viewer:** UI блокирует команды и показывает «только просмотр»; защита —
  серверная.
- **Presence:** рисуется поверх (курсоры/выделения в model space и на листе),
  список участников, индикатор синхронизации/ошибки.
- **Undo/redo:** кнопки шлют сообщения `undo`/`redo` на сервер; локальный стек
  не используется в совместной сессии. Redo доступен, пока участник не сделал
  новую операцию после отмены.

## 11. Тесты

Headless, 2–3 клиента, in-process сервер (без GUI); `cargo test` + отдельный
интеграционный набор `crates/collab/tests`. Список ниже — **план покрытия**, а
не отчёт о прогоне: команды и результаты гейтов живут в PR стека (#2935–#2938)
и `docs/STATUS.md`, этот PR их не исполнял.

1. Две операции над разными сущностями сходятся; состояния равны (сравнение
   `Drawing`).
2. Одна сущность: вторая правка даёт `conflict:true` и одинаковый результат.
3. Слои: создать/переименовать/удалить при активных участниках; сущности
   переезжают, `recordId` сохраняется; `laydel` — одна транзакция.
4. Блоки: переопределение и переименование при живых `INSERT`; атрибуты.
5. Размеры/штриховки: ассоциативность после чужой правки геометрии; границы.
6. Листы/вьюпорты: создание/удаление листа, `viewport.clip` на удалённый объект.
7. Порядок отрисовки: параллельные `draworder` сходятся по якорю.
8. Reconnect: догон по `version`, ресинк снапшотом, дедуп `opId` после рестарта.
9. Viewer: `op` → `forbidden`; presence проходит.
10. Undo/redo: два клиента отменяют каждый своё; отмена не трогает чужое;
    `undo-conflict`; redo возвращает отменённое; `redo-conflict` после чужой
    правки; новая операция сбрасывает redo-ветку; undo каскада слоя.
11. Большой чертёж: 10k+ сущностей, время diff и применения в бюджете; дельта
    не превышает лимит.
12. Commit: `.dxf`/`.dwg`, `notSaved`, 409 при внешнем изменении, идемпотентность;
    открытие в LibreCAD/QCAD (ручной gate, отмечен в PR).
13. Round-trip: commit → reopen → геометрия, слои, блоки, `foreign` совпадают
    (по `io::roundtrip::compare`; допуск — `1e-9` для координат, точные — для
    handle'ов, `recordId` и имён).
14. Роли и токены: матрица `viewer`/`editor`/`owner` × `op`/`undo`/`redo`/
    `commit`/`presence` — разрешённые и запрещённые случаи; протухший `exp`,
    чужой `iss`/`aud`/`fileId`, отзыв → `auth`/`forbidden`.
15. Лимиты и разрывы: чанки `applied{more:true}` без перемежения; `resync` в
    середине чанков; 1 MiB/8 MiB/5000 сущностей/50 операций в секунду;
    `rate-limited` + `hint.retryAfterMs`; дедуп после рестарта — тот же `opId`
    даёт тот же ответ, документ байт-в-байт прежний.
16. State и рестарт: журнал с пропуском, битой строкой и неполным хвостом;
    снапшот без sidecar; два поколения; `/healthz`, `/readyz`, `/metrics`.
17. Commit крупного файла: >512 KiB идёт по `uploadUrl`, `sha256` совпадает,
    `notSaved` передан; повтор с тем же `opId` не собирает файл заново.

## 12. Безопасность

JWT (ADR-0008), WSS, `Origin` для web, лимиты сообщений и операций, размер
документа, число участников. **Валидация входа** — строгая схема с закрытым
набором полей: `op`/`presence` проверяются по схеме до исполнения, глубина JSON
≤32, массивы (`selection`) ≤5000, неизвестные поля в `target`/`payload` —
`invalid`. Строки `sub`, `opId`, имена слоёв не попадают в логи сырыми:
структурные JSON-логи, управляющие символы вырезаются, длина ограничена.
Внешний bind — только за TLS/ingress; по умолчанию `127.0.0.1`, `Origin`
allowlist на upgrade, `/metrics` и health — loopback или токен. Логи: `sub`,
`opId`, `version`, коды ошибок; без содержимого, без токенов, без путей
пользователя. Снапшоты не отдаются в кабинет; commit — по контракту кабинета.
Антивирус/аудит — на стороне кабинета.

   **Решено в части политики:** default-deny, исполняются только адресуемые
   команды ADR-0018 и `primitive`-словарь; открыт вопрос, какой `primitive`
   входит в v1 (общий словарь на пять приложений или per-app, п.2).
2. Формат `primitive`-операций: общий словарь на пять приложений или per-app.
3. Порог «слишком большой операции» и поведение UI (разбить автоматически или
   предложить пользователю).
4. Место хранения журнала/снапшотов (volume, БД) и TTL после commit.
5. Нужен ли `read-only` флаг в `Session` (сейчас клиент блокирует до движка, а
   сервер — авторитет) и как пометить «команда меняет документ» в `CommandSpec`.
6. Различать окна одного пользователя. **Решено для presence и `opId`:**
   `welcome.clientId` (§3, §4.2), привязанный к `sub`; открыт только показ роли
   другого участника в панели (`participants[]` несёт `role`).
7. Формат манифеста снапшота и записей журнала: `format:1` в каждом; незнакомая
   версия при старте — отказ, а не догадка. Правило миграции — ADR-0005 п.1.
8. Индекс `version → offset` и сегментация журнала: сейчас реплей идёт с начала
   сегмента; нужен замер, чтобы назвать предел реплея.
9. Ключи и секреты: ротация `--secret-file`, проверочный асимметричный ключ,
   срок жизни и хранение `--dev-token` (только env/файл, только

10. Бенчмарки 10k/200k (`render::build`, DXF read/write, diff, `apply_remote`,
    `laydel`/`repoint`) — до того, как лимиты §9 считаются подтверждёнными;
